# 03 分阶段实施与学习清单

> 适用节奏：在职，每周 5～7 小时。<br>
> 建议周期：16 周左右，约 80～110 小时；先 V1 RAG，再 V2 Agent，最后 V3 评测与工程化。<br>
> 原则：Codex 负责样板代码、测试骨架和批量实现；使用者必须掌握数据流、技术取舍、代码审查、测试证据和 Bad Case 分析。

## 1. 总路线

| 阶段 | 建议周数 | 可运行结果 | 进入下一阶段门槛 |
|---|---:|---|---|
| 基线准备 | 1～2 周 | OCR/非 OCR 基线报告、公开测试语料 | 阻断项有结论，旧搜索回归稳定 |
| V1 RAG | 6～7 周 | 有引用的 RAG Demo，三种检索对比 | 15～30 条评测可复现，引用不伪造 |
| V2 Agent | 3～4 周 | 单 Agent/有限状态工作流调用一个真实工具 | 工具选择、参数、异常、超时和审计可验证 |
| V3 评测与工程化 | 4～5 周 | 自动化评测、Bad Case 优化、可观测性、演示资料 | 干净环境可启动，报告含真实前后对比 |

难度标记：低 / 中 / 高。标记“必须”的任务是后续依赖；“加分”可在时间不足时跳过。

### 3.2 V1 每周建议

- 第 2 周：R1～R3，先拿到块级证据。
- 第 3 周：R4～R6，完成 chunk 与 sidecar。
- 第 4 周：R7～R10，完成向量与混合检索。
- 第 5 周：R11～R14，完成回答、引用与安全策略。
- 第 6 周：R15，接现有 UI。
- 第 7 周：R16，跑第一轮评测并分析 Bad Case。
- 第 8 周：R17；有余力再做 R18/R19。

### 3.3 V1 可运行 Demo

1. 选择公开测试语料并构建旧索引。
2. 显示当前 generation，构建 RAG sidecar。
3. 输入一个精确术语问题和一个同义表达问题。
4. 分别切换 lexical/vector/hybrid，展示召回片段差异。
5. 生成带 `[S1]` 引用的答案，点击来源打开文件位置。
6. 输入无答案问题，系统明确拒答。
7. 展示评测结果文件和一个 Bad Case。

### 3.4 V1 回滚

- 配置关闭 RAG；旧 `SearchWorker` 和 `SearchEngine` 不变。
- sidecar 使用独立目录，删除/重命名即可停用。
- UI 新页面不可用时仍能回到原搜索页面。
- 每个任务单独提交，避免把 schema、模型、UI 一次混合提交。

## 6. 评测集设计清单

首批 15～30 条问题建议分布：

- 6～10 条明确术语/错误码，验证 lexical 基线；
- 4～8 条自然语言改写或同义表达，验证 vector/hybrid；
- 3～5 条跨段但不跨文档的问题，验证 chunk 与上下文；
- 3～5 条无答案问题，验证拒答；
- 2～4 条易混淆版本/型号问题，验证元数据过滤；
- 2～3 条 OCR 或表格问题，仅在相关基线修复后加入。

每条 Gold 至少包含：`case_id`、问题、允许的目标文档、相关 `stable_chunk_id`、答案要点、是否可回答、人工核对人、备注。模型生成的问题只能当候选，不能自动成为 Gold。

## 7. 每个增量的统一完成模板

每个 1～3 小时任务完成后都记录：

1. 功能目标和不在范围内的内容；
2. 修改文件；
3. 核心调用链；
4. 测试命令、样本和真实结果；
5. 已知失败与风险；
6. 回滚方式；
7. 使用者能否用自己的话解释设计。

如果第 7 项做不到，下一次学习时间优先补调用链和测试，不需要重复手写样板代码。

## 9. 面试表达核心技术点

### 9.1 项目定位

“我没有从零重写搜索工具，而是在一个真实的 Windows 本地全文检索项目上叠加 RAG。原项目已经有多格式解析、OCR、SQLite FTS5 和原子索引快照，我把它们抽象成可追溯证据层，再增加向量检索、混合排序、受约束生成和评测。”

### 9.2 关键取舍

- 保留 SQLite FTS5 作为精确术语分支，因为技术资料中的错误码、型号和参数非常适合词法检索。
- 向量索引用 sidecar，不改旧索引 schema，降低迁移和回滚风险。
- 用 RRF 合并排名，因为现有启发式分数和向量余弦不在同一尺度。
- 引用由程序生成并校验，模型只能选择来源编号，不能发明页码。
- 先单 Agent/状态机，不做多 Agent，以便控制超时、次数和错误。
- 先建立 Gold 数据和基线，再谈“优化”。

### 9.3 应准备的真实问题故事
