# 05 阶段 1：证据层代码级开发方案

> 对应 [04 方案的阶段 1](04_RAG缺失模块与详细设计方案.md)。证据模型、读取器、切块器和检查脚本已按此方案实现；后续 V1 的接口扩展见 [06 方案](06_RAG_V1完整闭环代码级开发方案.md)。范围是从当前**已发布**搜索 generation 只读提取 PDF、DOCX、TXT 的证据块，定义来源契约、切块规则和稳定 ID。

## 1. 交付边界与现有代码事实

| 交付物 | 文件 | 第一阶段的职责 |
|---|---|---|
| 证据模型 | `local_full_text_search/rag/models.py` | `SourceBlock`、`SourceRef`、`RagChunk`、`EvidenceChunk` 和错误类型 |
| 已发布块读取器 | `local_full_text_search/rag/block_reader.py` | 取得 generation 租约，在同一只读连接中流式读块及文件来源 |
| 切块器 | `local_full_text_search/rag/chunk_builder.py` | 按 PDF/DOCX/TXT 边界生成 chunk、偏移与稳定 ID |
| 人工检查入口 | `tools/inspect_rag_chunks.py` | 对指定文件输出 3～5 个 chunk 的 JSON，供人工核对来源 |
| 隔离测试 | `tests/rag/test_evidence_layer.py` | 锁定来源、版本、切块边界和稳定 ID 规则 |

现有 `ContentBlock` 有 `raw_text`、位置字段、`source_type`、OCR 置信度；`BlockCoalescer` 会把相邻 DOCX/TXT 小块合并，默认目标 4096、上限 16384 字符。已发布的紧凑快照通过 `search_blocks` 视图解码正文，其 `normalized_text` 只是空字符串占位，必须对 `raw_text` 重新调用 `normalize_text()`。紧凑快照的 `block_type` 是数值编码，不能当作原来的字符串使用。参考 `models/content_block.py`、`core/block_coalescer.py`、`core/compact_snapshot_schema.py`。

### 对 04 文档的一处验收修正

合并后的 DOCX 块只保留形如“正文第 1 段 - 正文第 8 段”的**范围**，没有可靠的逐段偏移映射。第一阶段可以准确引用这个已有范围，却不能承诺每个子 chunk 都有精确的单个段号。不得从换行数猜测段号，因为原文中的空段会被跳过。若以后必须精确到单段，需要在解析/合并阶段保留段落偏移映射，再经过新 generation 发布；那是单独的数据契约变更。TXT 有明确 `line_start/end`，PDF 有 `page_number`。

## 2. 文件与接口契约

### 2.1 `rag/models.py`

`source_id`（S1、S2）是生成答案时分配的临时编号，不属于第一阶段的持久来源模型。`file_id`、`document_id`、`block_id` 是**当前 generation 内**的定位键，不参与稳定 chunk ID。

```python
from dataclasses import dataclass


class NoPublishedGenerationError(RuntimeError): ...
class UnsupportedSnapshotError(RuntimeError): ...
class InvalidSourceError(ValueError): ...


@dataclass(frozen=True, slots=True)
class FileSource:
    file_id: int
    file_path: str
    filename: str
    extension: str
    parser_name: str
    parser_version: str


@dataclass(frozen=True, slots=True)
class SourceBlock:
    generation: int
    document_id: int
    block_id: int
    block_index: int
    block_kind: str              # PDF 页面、DOCX 段落/表格、TXT 等；未知则 "unknown"
    raw_text: str
    location_text: str
    page_number: int | None
    slide_number: int | None
    sheet_name: str | None
    cell_start: str | None
    cell_end: str | None
    line_start: int | None
    line_end: int | None
    source_type: str
    ocr_confidence: float | None


@dataclass(frozen=True, slots=True)
class SourceSpan:
    block_id: int
    block_index: int
    raw_start: int  # 原始块 raw_text 中的字符起点，左闭右开
    raw_end: int
    separator_before: str = ""  # 多块拼接时由切块器加入的分隔符


@dataclass(frozen=True, slots=True)
class SourceRef:
    generation: int
    stable_chunk_id: str
    file_id: int
    document_id: int
    file_path: str
    filename: str
    spans: tuple[SourceSpan, ...]  # 逐片段溯源；可精确覆盖跨块拼接和重叠
    block_index_start: int
    block_index_end: int
    location_text: str
    page_number: int | None = None
    line_start: int | None = None
    line_end: int | None = None
    source_type: str = "native_text"
    ocr_confidence: float | None = None


@dataclass(frozen=True, slots=True)
class RagChunk:
    stable_chunk_id: str
    text: str
    normalized_text: str
    text_hash: str
    chunk_policy_version: str
    sources: tuple[SourceRef, ...]  # 相同逻辑文档可能有多个真实文件路径


@dataclass(frozen=True, slots=True)
class EvidenceChunk:
    chunk: RagChunk
    selected_source: SourceRef  # 后续检索/引用时选用的一条仍存在的文件来源
```

实现时还应做 `__post_init__` 校验：文本不得为空；ID/路径不得为空；`spans` 非空且每段 `0 <= raw_start < raw_end`；`sources` 非空；所有来源的 `stable_chunk_id` 与 `RagChunk` 一致。逐段原文加上 `separator_before` 必须能重建 chunk 的 `text`；分隔符不能算作原始块中的字符。当前阶段无需设计 `RagAnswer`，因为答案生成属于阶段 4。

### 2.2 `rag/block_reader.py`

对外接口采用上下文管理器，使租约和数据库连接覆盖整个迭代期；不要返回一个在 `with` 外才开始消费的生成器。

```python
@dataclass(frozen=True, slots=True)
class DocumentBlocks:
    generation: int
    document_id: int
    files: tuple[FileSource, ...]
    blocks: tuple[SourceBlock, ...]


class BlockReader:
    def __init__(self, generation_base_path: Path) -> None: ...

    @contextmanager
    def open_active(self) -> Iterator["ActiveBlockReader"]: ...


class ActiveBlockReader:
    @property
    def generation(self) -> int: ...

    def iter_documents(
        self,
        *,
        file_ids: set[int] | None = None,
        extensions: frozenset[str] = frozenset({".pdf", ".docx", ".txt"}),
        limit: int | None = None,
    ) -> Iterator[DocumentBlocks]: ...
```

实现顺序：

1. `store = IndexGenerationStore(generation_base_path)`，调用 `store.acquire_active()`；没有 active 时抛 `NoPublishedGenerationError`，**不回退** `search_index.db`，也不枚举 `*.building.db`。
2. 用 `DatabaseManager(active.path, read_only=True).connect_read_only()` 打开连接。这个入口会注册紧凑视图所需的 `decode_text` SQLite 函数。先读 `snapshot_meta.generation` 与 manifest 的 generation 比较；不一致立即失败。
3. 显式 `BEGIN`，在同一个只读事务中获取文件与块；退出时先关闭连接，最后释放租约。取消或异常也走 `finally`。
4. 只选 `roots.enabled=1`、`files.parse_status IN ('success','metadata_only')`、`files.container_file_id IS NULL` 和所选扩展名。`source_type='metadata'` 的块不作为正文证据。ZIP 内部文件留给后续阶段。
5. 按 `documents.id` **键集分页**，每次取至多 128 个文档 ID；再批量获取关联文件和 `search_blocks`，按 `(document_id, block_index, id)` 排序。不要用一条 `files JOIN search_blocks` 查询直接返回块：同一文档对应多个文件时会重复每个正文块。
6. `FileSource` 按 `file_id` 排序；没有合格文件来源的文档不输出。一个文档的多个路径共享 chunk 文本，但各有独立 `SourceRef`。

文档分页和关联文件查询形状（`file_ids` 非空时额外加 `f.id IN (...)`；对同一批文档的文件查询也应用相同过滤）：

```sql
SELECT DISTINCT f.document_id
FROM files AS f JOIN roots AS r ON r.id = f.root_id
WHERE f.document_id > ? AND r.enabled = 1
  AND f.parse_status IN ('success', 'metadata_only')
  AND f.container_file_id IS NULL
  AND LOWER(f.extension) IN ('.pdf', '.docx', '.txt')
ORDER BY f.document_id
LIMIT 128;

SELECT f.id, f.document_id, f.path, f.filename, f.extension,
       f.parser_name, f.parser_version
FROM files AS f JOIN roots AS r ON r.id = f.root_id
WHERE f.document_id IN (?, ?, ...) AND r.enabled = 1
  AND f.parse_status IN ('success', 'metadata_only')
  AND f.container_file_id IS NULL
  AND LOWER(f.extension) IN ('.pdf', '.docx', '.txt')
ORDER BY f.document_id, f.id;
```

紧凑快照的正文查询形状：

```sql
SELECT b.id, b.document_id, b.block_index, b.block_type,
       b.raw_text, b.location_text, b.page_number,
       b.slide_number, b.sheet_name, b.cell_start, b.cell_end,
       b.line_start, b.line_end, b.source_type, b.ocr_confidence
FROM search_blocks AS b
WHERE b.document_id IN (?, ?, ...)
  AND b.source_type != 'metadata'
ORDER BY b.document_id, b.block_index, b.id;
```

`block_type` 数值编码由快照构造器的 `_code()` 产生。第一阶段为已知的 `pdf_page`、`pdf_page_ocr`、`docx_paragraph`、`docx_table_row`、`docx_header_footer`、`text` 建立显式编码映射，并在测试中与快照构造器对照；未知编码标为 `unknown`，只采用保守的单块切分。紧凑快照的 `ocr_confidence` 是原始浮点数乘以 10000 后保存的整数；读取器须除以 10000 还原为 0～1，普通结构则直接读取浮点数。兼容旧的非紧凑已发布库时，可检测 `search_blocks` 视图：不存在则从 `content_blocks` 读字符串 `block_type`；两条查询分别实现，不把两种 schema 混成一条动态 SQL。

这些 PDF 类型名称来自当前 `pdf_parser.py`；读取器单元测试仍须用解析器产出的真实 fixture 校验编码映射。

### 2.3 `rag/chunk_builder.py`

纯函数入口，输入一个 `DocumentBlocks`，输出有序 `RagChunk`；不打开文件、不查数据库、不调用模型。

```python
@dataclass(frozen=True, slots=True)
class ChunkPolicy:
    version: str = "evidence-v1"
    target_chars: int = 1000
    max_chars: int = 1400
    overlap_chars: int = 100


class ChunkBuilder:
    def __init__(self, policy: ChunkPolicy = ChunkPolicy()) -> None: ...
    def build(self, document: DocumentBlocks) -> list[RagChunk]: ...
```

**共同算法：**

1. 过滤空白块，保留其 `raw_text` 和来源位置。只在 `source_type`、格式边界兼容时拼接。输出 chunk 的 `text` 必须是来源原文的连续片段或带可验证分隔符的相邻片段；每个片段记录来源 `block_id` 和偏移。
2. 优先在空行、句末、整行边界切；不超过 `max_chars`。单个段落/行超过上限时才按字符硬切，保证至少前进一个字符，避免死循环。
3. 重叠优先使用完整行/句，最多 `overlap_chars`；只在同一页、同一来源类型、同一 DOCX 块类型内重复。重叠属于相邻 chunk 的文本，来源仍指向真实原文，不制造新的位置。
4. 对 `text` 计算 `normalized_text = normalize_text(text)` 和 `text_hash = sha256(text.encode('utf-8')).hexdigest()`。OCR 置信度取所用来源块中的最小非空值，不能把低置信度文字标成可靠原文。
5. 每个 chunk 为 `document.files` 中每个真实文件生成一条 `SourceRef`。文件名/路径只在来源中，不进入 chunk 内容 ID；后续阶段可复用一次 embedding 并选择一条有效来源展示。

**格式策略：**

| 格式 | 硬边界 | 可保真的位置 | 第一阶段的处理 |
|---|---|---|---|
| PDF | `page_number`、`source_type` | 页码 | 每页独立切；原生文字与 OCR 分开；页码缺失时不跨块 |
| DOCX | 段落块/表格行块/页眉页脚块类型 | `location_text` 范围 | 不混合正文、表格、页眉页脚；引用保留已有段落/表格范围，不伪造单段号 |
| TXT | 连续行 | `line_start/end` | 按行累计；切分后由原始换行计算真实起止行；过长单行仍引用该行 |

PDF parser、DOCX parser、TXT parser 以及 `BlockCoalescer` 的真实输出必须用于 fixture。`location_text` 若缺失，则把精度标为“块级”，不能生成猜测的位置字符串。页码和行号应从结构化字段取值。

### 2.4 稳定 ID 算法

不要把 `generation`、`file_id`、`document_id`、`block_id`、绝对路径写入 ID；这些值会随重建或移动改变。也不要仅用 `normalized_text` 当 ID，因为同一文档中可能重复同一句话。

```python
def canonical_digest(parts: list[str]) -> str:
    # 长度前缀避免 ["ab", "c"] 与 ["a", "bc"] 拼接歧义
    payload = b"".join(
        len(x.encode("utf-8")).to_bytes(8, "big") + x.encode("utf-8")
        for x in parts
    )
    return hashlib.sha256(payload).hexdigest()

# 同一逻辑文档的有序原文块内容与来源边界，连同 parser 名称/版本。
document_fingerprint = canonical_digest([
    parser_name, parser_version,
    *[canonical_digest([
        block.block_kind, block.location_text,
        str(block.page_number), str(block.line_start), str(block.line_end),
        block.source_type, block.raw_text,
    ]) for block in document.blocks],
])

stable_chunk_id = canonical_digest([
    policy.version, document_fingerprint,
    boundary_signature, str(chunk_ordinal_within_boundary), text_hash,
])
```

`boundary_signature` 由格式、页码/行号/位置范围、来源类型和源块序号组成。源块序号使用快照中的 `block_index` 仅描述**文档内逻辑顺序**；只要同样原文和策略生成同样顺序，跨 generation 稳定。对重复内容还加入边界内 chunk 序号。上述算法偏保守：文档任一块变化，会让该文档全部 ID 改变；阶段 2 若要更细粒度缓存，可在有评测证据后迭代策略版本。稳定 ID 是内容身份，`SourceRef.generation` 是本次可追溯来源，二者用途不同。

## 3. 实施顺序与每步可运行结果

1. **模型与校验**：建 `rag/__init__.py`、`models.py`；用纯对象测试空文本、偏移越界、来源 ID 不一致。此时无需数据库。
2. **读取器最小闭环**：用测试临时目录中的 `IndexGenerationStore` 发布 fixture，测试 `open_active()` 只返回 active generation；先支持紧凑快照，随后补旧结构读取分支。`decode_text` 必须通过 `DatabaseManager.connect_read_only()` 注册。
3. **PDF/TXT 切块**：先固定页码和行号、原文偏移、超长文本与重叠行为。用手工已知文本逐字符验证引用区间。
4. **DOCX 切块**：读取真实 parser + coalescer fixture，验证正文/表格不混合；位置仅承诺快照中的范围。
5. **稳定 ID 与多路径**：在两个不同 generation、不同本地行 ID 的等价 fixture 上比对 ID；改变文字或策略版本后确认 ID 改变；两个文件共享同一 `document_id` 时不重复生成 chunk，只产生两条来源。
6. **人工检查入口**：`python tools/inspect_rag_chunks.py --index-base <search_index.db> --file-id <id> --limit 5`。只输出 JSON 到 stdout，不写索引库。输出 generation、ID、文本摘要、路径、页/段范围/行号、来源块 ID 与逐段偏移，便于人工回到原文件核对。

## 4. 关键测试与验收

| 测试 | 核心断言 |
|---|---|
| 无 manifest、只有 building DB | 抛 `NoPublishedGenerationError`；不会读取 building DB |
| manifest 指向 gen N，另有 gen N+1 building | 所有输出 `generation == N` |
| 读取期间另一个 generation 发布 | 已开始的迭代仍读同一只读事务和 gen N；退出后租约释放 |
| PDF 两页与原生/OCR 混合 | chunk 不跨页、不混来源；低置信度被保留 |
| DOCX 段落、表格、页眉 | 三种类型不混合；只声明真实保留的位置范围 |
| TXT 两个 500 行原始块 | 按真实行号连续切；重叠区间的行号仍可核对 |
| 超长单行/单段和空文本 | 无空 chunk、无死循环、长度满足策略上限 |
| 两个 generation 相同内容、不同数据库 ID | `stable_chunk_id` 相同，`SourceRef.generation` 不同 |
| 重复段落、改变文本或 policy | 不同位置不碰撞；变化后 ID 改变 |
| 一个 document 对应两个 file | 只构建一份 chunk，`sources` 中有两条有效路径 |
| 旧搜索回归 | 现有 `SearchEngine` 测试保持通过，正式 schema 不变 |

验收时从**已发布** generation 导出 3～5 个 PDF/DOCX/TXT chunk，逐条核对文本确实来自对应源块、PDF 页码正确、TXT 行号正确、DOCX 位置范围不超出已有信息。测试只使用临时数据库与公开/模拟文件，不读取用户正式索引。建议运行隔离的 RAG 测试，再运行现有搜索核心回归；记录命令、通过数和未覆盖边界。

## 5. 风险、回滚与进入阶段 2 的门槛

- **位置精度**：DOCX 合并后不保留逐段偏移；阶段 1 引用范围必须如实呈现。后续若要精准段号，先修改解析数据契约并重建 generation。
- **版本一致性**：读取器持有 generation 租约与同一只读事务；任何跨 generation 拼接都视为错误。
- **内存**：每批最多 128 个文档 ID；单个巨大文档仍可能占用较多内存。先以单文档上限和观测记录控制风险，后续改为双遍流式指纹计算。
- **编码映射**：紧凑快照 `block_type` 为数值。已知类型映射必须用真实 fixture 检验；未知类型按单块处理。
- **回滚**：此阶段只新增 `rag/`、检查工具与测试，不修改原搜索 schema、发布流程、UI 或正式数据。移除新增入口即可回到原有行为。

进入阶段 2 的条件：证据模型固定、来源能人工核查、跨 generation 稳定 ID 测试通过、旧搜索回归通过，并记录 DOCX 引用精度限制。此时才把 `RagChunk` 写入独立 sidecar。
