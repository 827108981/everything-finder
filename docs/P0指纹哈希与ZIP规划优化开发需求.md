# P0 指纹、哈希与 ZIP 规划优化开发需求

## 1. 目标与现状

本需求针对首次全量索引和大目录增量更新的 P0 性能瓶颈。2026-08-17 的 6,404 文件实测中，总耗时约 5,805 秒，指纹/规划阶段约 5,196 秒，约占 89.5%；解析车道累计约 1,102 秒。因此本轮优先降低指纹阶段的重复读取、重复规划和逐条数据库提交，同时保持搜索结果完整性和增量更新正确性。

视频仍不在解析范围内。P0 优化不得通过跳过受支持文件、降低 OCR/正文精度或改变 ZIP 成员可见路径来换取速度。

## 2. P0-1 动态选择哈希去重或直接解析

1. 以已经取得的文件元数据（扩展名、大小、修改时间、来源类型、候选组数量、是否 ZIP 成员）做批次级决策，不为决策额外读取文件正文。
2. 只有在预计完整哈希读取成本低于共享解析结果的收益，或文件属于需要稳定成员内容身份的 ZIP/高成本解析格式时，才进入完整哈希；低成本文本、小型且重复度低的组允许直接解析。
3. 决策必须是确定性的、可回退的；决策异常时沿用直接解析，不得阻塞索引。
4. 物理文件只有在同扩展名/大小确有重复，或与已索引 ZIP 成员候选匹配时，才提升为候选。普通唯一文件不得因为静态扩展名规则被无条件完整哈希。
5. 记录候选组数、选择哈希的组数、选择直接解析的组数、决策耗时、完整哈希文件数/字节数、直接解析数和最终去重节省数。决策额外耗时目标不超过本批次规划耗时的 1%，且不超过 50 ms（取较小者）。
6. 任何策略变化都必须通过同一语料的命中数、正文内容、文件状态和增量复用回归测试。

## 3. P0-2 指纹与完整哈希复用

1. 同一索引运行中，同一物理文件或同一 ZIP 成员的完整 SHA-256 只允许计算一次；后续任务复用内存结果。
2. 跨运行复用已有完整哈希时，必须校验文件大小和修改时间纳秒值；不匹配时重新计算。
3. 指纹结果在批次末尾一次性写入数据库，使用单连接事务和 `executemany`，禁止每个文件单独打开连接并提交。
4. 哈希写入失败只能标记对应文件为可重试失败，不得中止整个索引批次，也不得弹出阻塞式错误窗口。
5. 计量区分元数据规划、指纹计算、完整哈希、哈希复用和数据库批量提交耗时，便于判断“减少解析时间”与“减少指纹确认时间”哪一项收益更大。

## 4. P0-3 ZIP 成员批量规划

1. 同一外层 ZIP 在一个规划批次内只打开一次并读取一次成员目录；成员按外层 ZIP 分组调度。
2. 在同一打开句柄内完成成员名称、索引、大小、CRC 和加密状态校验，并串行/受控地完成成员读取、SHA-256 和 spool 写入，避免每个成员重复打开 ZIP。
3. 单个成员校验或读取失败只影响该成员，其他成员继续处理；整个批次失败时回退到现有单成员任务，保证索引不中断。
4. 保留现有取消、暂停、安全检查点、临时文件原子替换和 ZIP 成员路径语义。
5. 记录 ZIP manifest 缓存命中、批次数、外层 ZIP 打开次数、成员准备数、成员读取字节数和批量准备耗时。目标是同一 ZIP 的句柄打开次数从“成员数级”降为“批次级”。

## 5. 数据与兼容性要求

- 现有数据库可直接升级；新增批量写入 API 不改变已有表结构和旧版本数据。
- 旧缓存、旧索引和无法取得元数据的文件继续走原有安全路径。
- 搜索、部分索引开放、暂停/取消、未成功索引列表和增量更新语义不得回归。

## 6. 验证门禁

### 6.1 代码测试

- 动态策略：廉价文本候选选择直接解析；PDF、图片、Office 或 ZIP 候选在预估收益足够时选择哈希；唯一文件不被提升。
- 批量哈希写入：一次事务更新多个文件，内容哈希和内容键正确。
- ZIP 批量成员：多成员 ZIP 返回全部成功结果；坏成员不影响其他成员；取消和失败可回退。
- 既有索引管线、ZIP、规划任务、指标和数据库回归测试通过。

### 6.2 真实语料快速验收

以 `E:\MRCODE\化免\免疫资料` 为测试集，执行一次可控的小批次或短时运行，核对：

1. 搜索命中数和正文与优化前抽样一致；
2. `fingerprint_ms`、完整哈希字节数、ZIP 成员准备次数和数据库写入次数可审计；
3. 无单个失败阻塞整个索引，无重复弹窗；
4. 已完成文件的后续增量更新不重复完整解析。

### 6.3 发布条件

所有 P0 测试和构建启动校验通过后才生成发行包。未完成真实语料验收时，状态只能标记为“代码完成/源码验收”，不得标记为“完全完成”或冻结版验收。
