## 7. 已知边界

1. OCR 是 CPU 密集型工作，开启后全量总耗时会明显增加；默认只有 1 个 OCR 进程、2 个 CPU 线程，并受独立字节预算约束。
2. ZIP 内部成员保持单 ZIP worker 顺序解析，避免解压临时文件和任务归属失控。
3. ETA 当前使用本次运行成本和实时速率，历史指标已落库但尚未训练跨运行预测模型。
4. 用户旧数据库升级会先生成 `.schema-vN.backup.db`，首次运行需要完整重建 FTS；不会直接覆盖旧文件。

## 9. 2026-07-27 卡顿问题修复复验

用户现场表现为索引停留在 `24 / 331` 数分钟，同时 UI 显示“预计剩余 1-4 秒”。本次排查确认存在三个叠加问题：

1. 旧版设置文件虽然明确保存了 `ocr_scanned_pdf=false`，但迁移代码会把旧版本 OCR 字段强制改为 `true`，导致 65 个 PDF 和 ZIP 内嵌 PDF 被错误送入 OCR 队列。
2. 索引调度线程同步递归读取整个子进程树内存，在 Windows 子进程繁忙或退出期间可能长时间阻塞，进度事件和超时检查因此一起停止。
3. 旧 ETA 使用所有队列的全局完成速率，最先完成的小文件会把预测压缩到数秒，无法反映仍在运行的大型 Office、OCR 或 ZIP 任务。

修复内容：

- 配置迁移保留用户显式设置，只为缺失字段使用默认值，并回写当前 `settings_version=3`。
- 普通、Office 进程、旧版 Office、OCR、ZIP 按独立队列成本和 worker 数计算关键路径 ETA；OCR/ZIP 使用保守先验，长任务超过静态预测后按实际运行时间扩展区间。
- UI 每 0.75 秒发送活动进度，展示实际正在运行时间最长的文件、队列类型、已运行时长和活动任务数。
- 资源采样移到独立后台线程，调度热路径不再同步遍历子进程树。
- 增加独立进程池 watchdog，即使主调度线程暂时背压，也能在单文件超时后回收 worker，并从检查点保留已解析正文。
- 取消/关闭时丢弃未写入队列并进行有界等待，避免 SQLite writer 队列导致“正在停止后台任务”长期不退出。

使用现场设置重新枚举 `E:\免疫资料` 后，331 个任务分流为：普通 131、Office 进程 180、旧版 Office 13、ZIP 1、图片 OCR 6；65 个 PDF 不再进入 OCR 队列。真实全量复验结果：

## 10. 旧数据库全量重建写锁修复

现场错误为 `sqlite3.OperationalError: database is locked`，两次均发生在调度线程调用 `mark_tasks_running()` 时。SQLite 已配置 30 秒 `busy_timeout`，因此可以确认另一个写事务持续持锁超过 30 秒，而不是瞬时竞争。

现场数据库检查结果：

- 数据库大小 228,298,752 bytes，`PRAGMA quick_check=ok`，数据库本身没有损坏。
- 仅有一个应用实例，排除两个 EXE 同时写入。
- `content_fts` 有 40,293 条旧记录，数据库同时标记 `schema_v3_rebuild_required=1`、`full_batch_incomplete=1`。
- 旧删除语句按 FTS5 的未索引 `block_id` 列过滤，查询计划为 `SCAN content_fts VIRTUAL TABLE INDEX 0:`；每更新一个文档都会扫描整个 FTS 表。
- 全量重建虽然已经计划在最后统一构建 FTS，但正文写入阶段仍逐文档删除旧 FTS，导致单批事务持锁数分钟，并与任务状态写入竞争。

修复内容：

1. 全量延迟 FTS 模式下，正文写入只替换 `content_blocks`，不再逐文档修改旧 FTS；旧 FTS 保留到最后一次性重建。
2. 增量更新仍需即时删除 FTS 时，改用与正文块主键一致的 `content_fts.rowid` 精确删除，查询计划变为 `VIRTUAL TABLE INDEX 0:=`。
3. 文档垃圾回收、旧 schema-v2 正文和失败状态清理均遵循相同的 `update_fts` 策略，避免旁路再次触发全表扫描。
4. 新增 `--validate-database-lock` 验证器，在源码和冻结 EXE 中制造 40,000 条旧 FTS 数据和 64 个并行重建文件。
5. `running`、`processing` 和 `spooled` 属于可恢复的中间诊断状态，调度热路径改为零等待尽力写入；SQLite 正在提交正文时立即跳过，不再等待 30 秒并中止整轮索引。最终 `complete` 和正文块仍由单一 `IndexWriter` 严格事务提交。
6. 数据库连接初始化也纳入 `try/finally`，即使连接级 PRAGMA 遇到锁也会关闭句柄，避免 Windows 文件句柄泄漏；慢于 5 秒的正文写入批次会记录明确告警。

## 11. 2026-07-28 重新更新停滞与 OCR 超时修复

现场复现为重新更新停在图片任务，界面长时间显示 `正在解析并写入索引 76 / 331`。本次没有依据截图猜测，而是先停止应用、对 228,298,752 bytes 的现场数据库制作一致性副本，再在真实 `E:\免疫资料` 上重复执行更新。

### 11.1 根因

1. schema-v3 数据库的 `short_tokens` 有 2,801,176 行，但没有以 `block_id` 为首列的索引。替换正文块时，外键级联删除会反复全表扫描 `short_tokens`；真实日志中 9 个 artifact、27 个 block 的单批 SQLite 写入达到 55,131 ms。
2. 旧 OCR 使用 PP-OCRv6 medium 检测/识别模型。密集图片单张可超过 120 秒，6 张现场图片累计全部超时；因此即使数据库写锁消除，重新更新仍会卡在 OCR 队列。
3. Paddle 在 Windows 下不能稳定读取中文源图片路径；直接传入 `E:\免疫资料\...jpg` 时曾出现 `OSError: Invalid argument`。
4. 旧默认 OCR 长边 2400 会让复杂背景产生大量误检测框，检测耗时呈非线性增长。现场第一张图片即使换成移动模型，在 1280 下仍超过 120 秒；缩放到 960 后为 19.8 秒。

### 11.2 修复

- 数据库升级到 schema v4。升级前自动保留 schema-v3 数据库备份，删除可重建的旧 `short_tokens` 派生缓存，并创建 `idx_short_tokens_block(block_id)`；v3 升 v4 不强制丢弃已成功的正文解析结果。
- `DatabaseManager` 跟踪活动 SQLite 连接；强制停止和 writer abort 会调用 `sqlite3.Connection.interrupt()`，避免关闭窗口时等待长 SQL。
- OCR 固定使用随包提供的 `PP-OCRv4_mobile_det` 和 `PP-OCRv4_mobile_rec`，同时显式绑定模型名与目录，避免 PaddleOCR 3.7 回退到 v6 默认管线。
- 关闭方向分类和 MKLDNN，限制 CPU 线程；所有中文图片路径先转存到 ASCII 临时路径。
- OCR 默认长边从 2400 改为 960，设置版本升级到 v4。只迁移仍等于旧默认值 2400 的配置，其他用户自定义值保留。
- 图片解析器版本升级到 3，OCR 缓存命名空间升级，确保“重新更新”会使用新模型而不是复用旧结果。
- 打包只收集两个移动端模型，不再包含旧方向模型和两个 v6 medium 模型。
