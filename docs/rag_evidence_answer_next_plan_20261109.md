# RAG 证据与回答流程后续计划

- 日期：2026-11-09（Asia/Shanghai）
- 依据：[完整验证计划](E:/code/everything-finder/docs/rag_evidence_answer_validation_plan_20261108.md)
- 当前结论：可以合并一部分代码，但只合并稳定的评测基础设施，不合并尚未通过门槛的回答行为候选。
- 当前候选状态：暂不采用。上一轮完整验证已发现候选在 050、独立题 04、035、019、032 等位置存在跨对象误用、关键事实丢失或无依据扩展，不能因为部分题改善就切换默认问答流程。

## 1. 这次要解决的两个问题

后续工作要把两个容易混在一起的问题拆开：

1. **代码问题**：多个一次性实验脚本重复实现了文件读写、哈希、配置读取、JSONL 处理、批量配对、重试、结果保存、来源核验和摘要统计。重复实现会造成入口不一致、结果格式不一致、修一个脚本漏另一个脚本，以及实验代码互相导入形成隐性依赖。
2. **回答问题**：证据整理候选是否能改善真实回答。这个问题仍未通过完整验证，尤其是对象适用性和必答事实保留还没有达到采用门槛。

代码整理不能被当成回答质量改进；回答候选也不能借代码重构顺便改变输入、提示、选段或评分。两项工作必须分别验证、分别报告、分别决定是否采用。

## 2. 可以合并、暂缓合并和不应合并的内容

### 2.1 第一批可以合并的内容：只放评测基础设施

建议新增一个评测公共模块，例如 `tools/rag_eval_common.py`，或者放在 `tests/rag/support/` 下。它只能提供纯工具，不进入生产问答路径。

可以抽取的函数包括：

- JSON、JSONL 的安全读写和逐行解析；
- 文件、目录、配置、Gold、索引清单和候选代码的 SHA-256 计算；
- 非敏感模型配置和当前 AI bundle 的读取；
- API 密钥脱敏、异常文本截断和统一运行元数据；
- 配对任务生成、轮次编号、A/B 交替顺序和重试状态记录；
- 结果文件的追加写入、完成数、失败数、缺测数、复用数统计；
- 原文、索引正文、实际发送上下文的哈希及来源绑定记录；
- 统一的 `protocol.json`、`input_manifest.json` 和 `execution_log.md` 写入格式。

这些函数不应知道题号、报警码、机型、答案关键词或某个业务项目。它们只能处理输入和元数据。

### 2.2 第二批可以合并的内容：通用的只读核验器

在第一批通过后，新增 `tools/rag_trace_audit.py`，只负责审计，不改变上下文和回答：

- 检查 Gold 引文是否存在于原资料；
- 检查同一引文是否存在于当前 AI 索引正文；
- 检查实际发送文本是否真的包含该段正文；
- 记录来源文件、页码或幻灯片、chunk、实际上下文和断言的绑定关系；
- 标记对象、机型、方法、阶段、表格行列、单位或版本未确认的情况；
- 把“资料不存在”“资料未进索引”“索引命中但未入上下文”“进入上下文但回答漏用”“回答引用不支持断言”分开记录。

这个模块可以复用生产侧的 `gold_loader.py`、`evidence_matcher.py`、`context_builder.py` 和 `citation_validator.py`，但不能反向修改它们的业务行为。

### 2.3 第三批可以考虑合并的内容：通用的配对执行器

只有前两批验证通过后，才考虑把 `answer_scene_guard.py`、`verify_scene_guard_cross_source.py`、`validate_evidence_answer_flow.py` 中重复的批量执行骨架抽成 `tools/rag_eval_runner.py`：

- 接收一个明确的输入上下文和一个候选策略；
- 对同一个请求运行 A/B；
- 保存实际问题、上下文哈希、实际答案、引用、裁判结果和异常；
- 支持首轮和预定复测，不支持“看答案好坏再选择性重试”；
- 支持把生成器或策略作为依赖注入，而不是在公共执行器里写死某个候选。

这个执行器只负责运行和记录，不能把证据整理、场景守卫、行级补充、重排规则或答案关键词写进去。

### 2.4 暂缓合并的内容：实验候选和场景策略

以下内容暂不进入生产，也不和公共基础设施一起合并：

- `ExperimentalGateway`；
- `PLAN_PROMPT`、`ANSWER_PROMPT` 及证据清单两阶段调用；
- `validate_map` 中对引文和适用性的实验性判断；
- `scene_guard`、`method_guard`、`row_holdout`、`material_steps` 等针对特定实验的规则；
- 直接 monkeypatch `runner.Experiment` 或替换生成器的实验入口；
- 只为 019、035、050、021 等单题服务的特殊分支；
- 报告中固定写死题号、答案短语或资料文件名的统计逻辑。

这些代码仍可保留在实验目录中，作为可重复的候选版本，但不能影响默认的 `AnswerService`、召回、选段、澄清、拒答和生成流程。

### 2.5 不建议合并的内容：复制生产类

`AnswerService`、`QueryInterpreter`、`GoldAnswerJudge`、`RagIndexStore`、`OpenAICompatibleGateway` 等生产类不应在 `tools/` 下复制或重新包装成第二套业务实现。实验脚本应直接导入生产类，并通过参数或依赖注入替换候选策略。否则会出现“实验通过但真实入口不一致”的问题。

## 3. 完整执行顺序

下面的顺序对应完整验证计划的输入冻结、证据核验、隔离实验、真实入口回归和采用决定。每一步都必须有结果文件和明确结论，不能做完代码合并就提前结束。

### 第 0 步：冻结当前状态

目标是保证重构前后可以比较。

操作：

1. 读取完整验证计划、上一轮报告、当前冻结记录和当前生产入口。
2. 记录 Git HEAD、工作区差异、当前已发布 AI bundle、模型标识、配置哈希、Gold 和回归集哈希。
3. 保存当前 `AnswerService`、`OpenAICompatibleGateway`、`GoldAnswerJudge`、评测 runner 和报告模块的哈希。
4. 确认默认测试集没有切换到候选版本，历史 18 题和 v1/v2/v3 历史结果不被覆盖。
5. 建立新目录，例如 `reports/rag_code_consolidation_20261109/`。

产出：`protocol.json`、`input_manifest_before.json`、`execution_log.md`。

完成标准：能明确说明重构前实际使用的入口和输入，工作区已有改动原样保留。

### 第 1 步：建立代码重复与依赖清单

目标是确认哪些重复是真重复，哪些只是不同实验的业务策略。

检查：

- 所有 `tools/*.py` 的 `read`、`write`、`lines`、`sha`、`dump`、`model_settings`、批量任务、重试、结果汇总函数；
- 是否存在从实验脚本导入另一个实验脚本的链路；
- 是否在 `tools/` 重复定义生产类或重新拼装生产流程；
- 每个函数的调用者、输入输出格式、是否会影响问答行为；
- 是否读 Gold、题号或答案作为运行时逻辑，而不是只供评测。

产出：`code_overlap_inventory.json`、`code_dependency_graph.md`。

判定：

- 纯读写、哈希、统计且不含业务词的函数列入第一批；
- 只负责审计来源绑定的函数列入第二批；
- 包含对象、条件、场景或答案策略的函数保持实验隔离；
- 生产类复制、实验脚本相互隐式导入列为待拆依赖。

### 第 2 步：先抽取公共评测工具，不改变任何实验行为

目标是把重复的基础代码集中起来，同时保持每个实验的输入、提示、上下文和结果不变。

实施约束：

1. 新模块只能依赖标准库和生产侧只读数据接口。
2. 不在新模块内导入 `validate_scene_guard.py`、`validate_scene_quota.py` 或其他业务实验脚本。
3. 每个原脚本先改为调用公共函数，再删除其本地重复实现；每次只改一个功能类别。
4. 所有输出字段保持兼容，旧报告可以继续读取。
5. 公共模块不得自动修改 Gold 状态，不得切换默认测试集，不得自动采用候选。

首批建议顺序：

1. JSON/JSONL 与哈希；
2. 脱敏和运行元数据；
3. 配对任务、重试和结果落盘；
4. 证据来源核验；
5. 统计汇总。

每完成一个类别就运行对应的回归检查，不能一次性大改后再寻找差异。

### 第 3 步：验证“只重构、不改变行为”

这一步不调用模型，优先用已有结果和本地可复现输入。

必须检查：

- 旧 JSON、JSONL、Markdown 报告仍能被加载；
- 同一个输入的源文件哈希、索引 bundle、上下文哈希完全一致；
- 配对顺序、轮次、重试和缺测统计一致；
- 旧报告的逐题 A/B 输出、裁判结果和分母不被重写；
- 默认入口的答案流程没有增加证据整理调用；
- 生产类导入路径没有改变；
- 67 项已有相关测试及新增公共工具单测全部通过。

产出：`refactor_compatibility.md`、`before_after_manifest.json`。

通过条件：所有差异只能是文件路径、代码位置或格式化差异，不能是上下文、答案、评分或题目状态差异。失败则回退公共抽取，不进入回答候选实验。

### 第 4 步：验证只读证据审计器

目标是先确认“实际引文与对象绑定检查”可靠，再用它判断回答候选。

固定样本：

- 现有报告中 019、035、050、021；
- 已确认的 008、015、016；
- 独立集中的跨机型、跨方法和相邻页样本；
- 至少一个表格、一个跨页、一个步骤链、一个资料不足题。

每题记录：

1. 原资料位置和原句；
2. 当前索引 chunk 和正文；
3. 实际发送上下文；
4. 断言对应的对象、条件、顺序、单位；
5. 证据是否足以支持断言；
6. 最早失败环节。

产出：`source_audit_replay.jsonl`、`source_audit_replay.md`。

通过条件：审计器不会把同页其他内容、相邻页、同报警码或同部件号自动算作正向支持；不会把 Gold 中未实际发送的文字当成上下文。

### 第 5 步：重新执行完整的回答候选验证

只有第 3、4 步通过后，才重新执行回答候选。代码重构和候选行为必须使用不同的输入哈希和报告目录。

按完整计划执行：

1. 开发集 12 题，A/B 各 3 次；
2. 独立验收集 12 题，运行前冻结，A/B 各 3 次；
3. 正式集、原回归集和独立集分别报告；
4. 关键改善、退步和不确定项按预定规则补两次；
5. 保存实际上下文、实际回答、实际引用、证据清单和裁判原判；
6. 不从 Gold 读取必答事实给回答模型；
7. 不因为候选分数不好就更改提示再混算；
8. 发现新的跨对象误用或关键事实丢失，立即把候选标为失败版本，但仍完成已冻结的剩余只读对照。

重点复核：

- 050 是否把免疫场景化资料中的通用排查方向完整保留，且不越界到未经确认的机型参数；
- 019 是否保持项目范围和“多数项目”条件，不把单项目证据扩展为全局结论；
- 035 是否在最终答案中保留主要原因和用户实际询问的处理结论；
- 021 是否表达两条条件分支，不把 LVC 直接归因给上次或本次试剂；
- 独立题 04 是否发生 CL-8000i/CL-8200i 资料误用；
- 任何证据清单正确但答案漏答的情况是否被单独记录。

### 第 6 步：分别作出两个采用决定

代码基础设施和回答行为不能共用一个“通过”结论。

#### 评测基础设施采用条件

- 重构前后默认问答输出不变；
- 历史报告和当前评测结果可以加载；
- 实际上下文、来源绑定和哈希检查一致；
- 运行失败、重试、缺测和脱敏行为有测试；
- 没有实验脚本反向改变生产类行为。

满足后，可以合并第一批公共评测代码。

#### 回答候选采用条件

- 至少两个不同业务组有原文核实的改善；
- 至少一个业务组在重复运行中保持改善；
- 独立验收出现同机制收益；
- 没有新增已确认的错对象、错条件、关键事实丢失或无依据处理建议；
- 正式集、回归集和独立集的分母、缺测和争议项清楚分开。

当前上一轮结果不满足这些条件，所以回答候选继续保持隔离，不合并到生产。

### 第 7 步：合并后的回归和发布控制

若只有公共评测工具满足条件：

1. 只合并公共工具和相应测试；
2. 保留实验候选脚本和报告作为历史证据，但不接入默认入口；
3. 运行默认问答的冒烟测试和评测加载测试；
4. 检查 v1/v2 历史用例、当前 v3 Gold 和回归集状态不变；
5. 在变更说明中明确“此次合并只整理评测代码，不改变问答算法”。

若回答候选后来通过：

1. 另建候选变更，不能和基础设施重构混成一个无法归因的提交；
2. 先通过正常入口做小规模灰度或离线回放；
3. 记录新 bundle、配置、提示和代码哈希；
4. 保留回滚开关和 A/B 对照；
5. 只有真实入口复核通过后，才讨论默认开启。

## 4. 当前建议的合并拆分

建议拆成三个独立变更单元：

| 变更单元 | 内容 | 当前动作 | 通过后结果 |
|---|---|---|---|
| A | 评测公共读写、哈希、脱敏、任务和结果记录 | 可以开始整理 | 合并到评测工具层 |
| B | 原文—索引—实际上下文—对象绑定审计 | 在 A 通过后做 | 合并到只读核验工具层 |
| C | 证据清单后再回答的候选流程 | 保持隔离，重新按完整计划验证 | 当前不进入生产 |

不要把 A、B、C 放进同一个提交。这样即使 C 再次失败，也不会影响已经验证过的评测基础设施；如果 A 或 B 引入差异，也能单独回退。

## 5. 结束条件和最终交付

本轮不能用“代码更整齐”作为完成标准，必须交付：

- `code_overlap_inventory.json`；
- `code_dependency_graph.md`；
- `refactor_compatibility.md`；
- `source_audit_replay.jsonl`；
- 按完整验证计划生成的新回答候选报告；
- 基础设施采用决定和回答候选采用决定；
- 逐题列出变好、变坏、不变、缺测和争议；
- 当前 AI bundle、配置、Gold、代码和报告的结束哈希；
- 明确说明哪些代码合并了、哪些仍留在实验区、哪些行为没有改变。

最终结论只能取以下之一：

- **建议合并评测基础设施，回答候选暂不采用**；
- **评测基础设施和回答候选均满足门槛，可分别合并**；
- **基础设施重构本身引入行为差异，全部暂缓并回退**。

按照当前已有证据，下一步的默认路径是第一种：先整理并验证公共评测基础设施，再单独验证回答候选；不能因为重复代码很多，就把尚未通过验证的回答规则一起并入生产。
