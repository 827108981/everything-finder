## 2. 已确认的代码问题

- `generation/openai_compatible.py` 的生成提示要求资料不足时只输出固定拒答，未完整定义部分回答和必须追问。
- `query_interpreter.py::_missing_fields()` 返回空元组；它避免了按缺少固定字段盲目追问，也意味着不能靠它判断盘型、定标数据、通讯方式是否真的必要。
- 当前配置未指定 `rag_semantic_clarification_enabled`，应用默认false；已有语义澄清候选没有在当前问答中启用。它属于未充分验证的候选，不能直接打开并宣称修复完成。
- `answer_service.py` 对固定拒答字符串单独处理，其他生成文本进入最终引用校验并标记ANSWERED。只让模型在普通生成中输出一个无引用追问，不能保证应用状态及校验行为正确。
- 当前答案二次审查关闭。首版不引入常驻的“再规划、再生成、再审查”多轮调用。

## 3. 通用决策规则

先按用户实际诉求识别需要回答的部分，保留用户问句中的对应片段，不能把资料里出现的每一项都当作用户要求。

|每部分的情况|行为|禁止的退化|
|原文支持且适用条件明确|回答必要事实、顺序、单位、引用|照搬无关背景或把限定机型阈值扩大使用|
|不同答案取决于用户能确认、但尚未提供的条件|询问决定选择的最小条件；不提前确定分支|仅因缺少某固定字段就追问；用列出分支代替确认当前选择|
|用户问一般原理、对比或通用排查|回答共性或明确区分分支|把概念问题变成机型、阶段等信息收集问卷|
|部分有据、部分原文没有依据|保留有据答案，指出具体缺口|因一个子问题缺资料而整体拒答|
|现象本身不足以确定故障，但可以判断不能直接确定|直接说明不能确定，给资料支持的必要解释|把“不能直接确定”的可回答问题一律改成追问|
|所有实质诉求均缺少适用证据|说明无法依据现有资料回答|猜测答案或把资料缺失伪装成用户没提供信息|
|相同适用条件下资料冲突|说明冲突及来源、暂不给唯一结论|让用户任意选择一个答案；静默优先某个数字|

复合问题允许“先回答可回答部分，再追问剩余部分”。内部需同时记录部分回答和待补条件；不要强迫所有复合情况只剩一个全局布尔值。

这些规则不包含题号、文件名、报警码或特定机型的硬编码。

## 4. 首版实现范围

### 4.1 一次模型请求，返回结构化结果

在现有生成接口增加版本化候选协议，模型在同一个请求中给出简短的决策记录及最终答案。接口不依赖服务商必须支持某种JSON Schema功能；本地必须验证返回结构。

建议字段：

- `parts`：用户诉求对应的原话片段、`supported / needs_user_input / evidence_missing / evidence_conflict`状态。
- `evidence`：该部分引用的真实S编号、短原文定位。只存必要核验信息，不要求输出冗长推理过程。
- `missing_fields`与`follow_up`：仅对确实决定分支的用户条件填写。只问当前需要的最少信息。
- `answer_text`：只包含面向用户的回答，保留每项事实的引用。

服务端根据各部分状态组合确定最终行为，不以模型给出的一个全局标签作为唯一依据。事实引用存在不等于事实被支持；结构验证无法替代语义复查。

正常路径仍是一次LLM调用。格式错误最多恢复一次，记录额外调用；超时、解析错误应作为执行失败报告，不能转成业务性的“资料不足”。不根据答案分数重试。

### 4.2 服务层接线

涉及：`generation/base.py`、`generation/openai_compatible.py`、`answer_service.py`，必要时增加一个小型解析/校验模块。

- 纯追问映射现有NEEDS_CLARIFICATION，保留最小待补字段；不能按普通有事实答案要求它一定带引用。
- 有事实的答案必须通过引用校验；部分回答同样需要引用有据部分。
- 纯拒答映射INSUFFICIENT；执行异常不映射INSUFFICIENT。
- 部分回答可继续使用现有ANSWERED状态，增加兼容性的行为元数据及待补字段，避免立刻改动所有UI状态枚举。
- 回答中附带澄清时保留答案与澄清信息，不因出现follow_up丢弃已回答内容。
- 候选模式使用一个开关且默认关闭；候选启用时不再同时运行旧的独立语义澄清候选。开关关闭恢复原路径。
- 核查UI、批量评测和trace对返回状态的理解一致。不得仅在独立脚本中看起来答对，而真实应用仍报引用错误。
- 若未来与答案二次审查同时启用，审查器也必须支持部分回答/追问；这项组合未经验证前不纳入首版采用范围。

### 4.3 评测适配

运行结果记录实际行为及各诉求状态，Gold仍仅用于离线评估。生成请求不得接收Gold的expected_behavior、required_facts、missing_fields或题号提示。

保留现有Gold裁判结果，另列人工语义复查和额外主张。不能因为输出了clarify标签就判成功，必须检查实际追问是否针对决定答案的条件；不能因为引用格式正确就判事实正确。

## 6. 后续资料侧修复顺序

回答修复采用并形成新基线后，再独立处理下面的瓶颈，每次只改一个机制。

|次序|机制|通用实现方向|保护条件|
|---|---|---|---|
|1|最终片段数量/文档配额丢掉独有内容（006、023）|研究按用户实际诉求核对已选证据是否覆盖；只有候选能补足未覆盖诉求时才考虑替换重复片段或有限放宽同文档配额|保留适用条件优先级；不得直接取消所有配额或让原始重排分覆盖最终条件顺序；替换前确认已有必要内容仍有支持|
|2|标题场景与后页步骤分离（019）|构建可追溯的章节/续页关系，检索命中场景时带回同一小节的处理页|同文件同版本，有明确结构证据；不把任意相邻页绑定，不跨新标题合并|
|3|多部分问题有一部分未召回（040、050）|按用户原话提取独立诉求，原问保留，有限补充检索缺口分支|不自动补机型/症状/结论；最多一次有预算的补查；单问题不增加循环检索|

这些属于后续候选方向，其通用“覆盖判定”本身也可能出错，必须先验证，不能以“检查覆盖”为名重新引入未经验证的强规则。已有A/B及选片实验不能直接视为这些机制已通过。

资料侧先做候选/最终证据保留检查，并人工复查相似机型、表格同页、同正文不同格式。只有证据检查通过，才运行回答评测；出现正确必需内容丢失或实际错场景进入时停止该候选，避免继续花费模型调用。
