# 条件检查更改与验证方案（2026-11-18，待实施）

## 1. 目标与冻结基线

目标：条件检查不能破坏已经较好的相关性排序；只有能够定位到原文、对象一致且确实不适用的证据才能被硬排除。保留“不知道是否适用”的状态，不把它伪装成匹配或冲突。

本计划只提出方案，不修改业务代码、Gold或运行默认配置。

基线为已采用的BGE分窗口最高分：每窗最多512 token、重叠64 token、模型基础分排序。API前全部111题结果位于`reports/rag_bge_windows_20261118/window_max_native.jsonl`，接入核验位于`reports/rag_bge_window_adoption_20261118/`。

冻结：问题、Gold、索引包、切片、BM25、向量、RRF、去重、重排入口20、BGE窗口与分数、最终Top8、0.1门槛、12000字符预算、Domain Adapter默认关闭。未经单独实验，不改变这些项目。

111题分开报告：50题已审核，其中46题有正向Gold；41题诊断，其中40题有正向Gold；20题来源保留pending。007保持disputed。没有Gold的题不能用“没有命中金标”判定检索失败，诊断题不混入正式计分。

## 2. 当前代码中的三个问题

### 2.1 适用性标签成了第二套排序分数

`constraint_matcher.py`按以下顺序排序：未冲突优先、没有UNKNOWN优先、条件分数高优先。条件分数为硬匹配数×2＋软匹配数－软冲突数；仅有软条件时也会重排。

因此，正文出现一个“样本”的低相关资料可能排在真正提供条码参数、但没有重复“样本”的高相关表格前面。免疫条码两份Gold由BGE第2/3降至条件后15/16，最终Top8丢失；生化条码尺寸题由2降至14，最终经低分过滤仍保留第7。

这不是UNKNOWN判为CONFLICT，而是UNKNOWN遭到过强的排序惩罚，两者要分别修复。

### 2.2 提及词语不等于对当前事实建立适用关系

当前OBJECT判定在正文和文件名组合文本中查找词语；阶段/方向等会在较大文本范围中查找相同或相反表达。问题包括：

- “样本条码”中的“样本”是复合对象的一部分，不能证明当前问题属于样本检测阶段。
- “结果偏低时重新定标”中的“定标”是处理动作，不必与当前样本检测阶段冲突。
- 一个片段同时列出多个型号/多个分支，不能仅因出现其他型号或一个不匹配分支而整段删除。
- 文件名可以提供来源线索，但标题中的一个词不能自动证明正文每个事实适用。

现有判定通常知道词出现了，却不知道它约束的是哪一个事实。

### 2.3 保留UNKNOWN后，其他模块仍可能清空证据

`evidence_policy.py`在最终选段后检查scope、stage、direction、device、topic等硬条件；如果没有最终候选得到对应MATCH，可能返回`required_constraint_not_confirmed`并清空已选证据。

`clarification.py`也会根据候选阶段作追问判断。第一轮不修改追问策略，但必须记录它是否因条件标签变化而提前结束检索。

因此“取消UNKNOWN后移”和“UNKNOWN一定能进入最终Context”不是同一件事。要记录具体在哪个门禁退出，不得把两个变化混称为条件检查收益。

## 3. 最终职责划分

```text
BGE窗口最高分：判断候选与问题的相关程度并排序
    ↓
条件检查：记录每个条件的匹配/冲突/未知，附原文依据
    ↓
最终证据筛选：剔除已证实冲突，按原相关性顺序应用既有门槛与TopK
    ↓
Context：保留原文及尚未确认的适用范围说明
```

不增加第二个排序模型、不增加领域答案知识图、不调用生成或裁判API。条件模块没有足够证据时允许不知道，不承诺规则能理解所有中文。

## 4. 修改A：条件模块保留BGE顺序

这是第一步，也是最小、最容易归因的实验。

### 行为

1. 逐候选执行原有条件判定，暂不改任何MATCH/UNKNOWN/CONFLICT结果。
2. 不依据MATCH数量、UNKNOWN数量、软条件分数改变候选顺序。
3. 条件阶段展示全部候选及标签，保持BGE输入顺序。
4. 最终门禁仍按当前判定剔除CONFLICT；剩余候选保持BGE相对顺序。
5. `constraint_score`若保留，只作历史诊断，不再作为排序依据。
6. 现有最终硬条件覆盖门禁先不改；如触发清空，明确记录为A仍未解决的后续问题。

### 必须保持的性质

- 对任意两个非冲突候选，条件检查前后的相对顺序一致。
- UNKNOWN和MATCH之间没有新的固定配额或分数奖励。
- 明确冲突候选仍不能凭高BGE分直接进入Context。
- 不改变原问题/关键词/向量查询，不把Gold引文当作保护候选。

A验证的是“旧条件排序是否破坏相关性”，不是证明原有适用性判定正确。

## 5. 修改B：条件判定依据绑定到对象、属性和局部事实

第二步单独验证，不直接启用11月15日已知误删的方法。复用现有QueryConstraint、ConstraintJudgement、CandidateDecision和日志字段；新逻辑可注入，对照期间不作为默认。

### 5.1 三态定义

|状态|允许成立的依据|不允许的推断|
|---|---|---|
|MATCH|问题条件与当前事实在正文、可追溯表头/章节中建立同一对象、同一属性的关系|出现同一个词就认为适用|
|CONFLICT|同一目标事实明确受不相容条件约束，且不能通过同片段其他目标分支解释|没出现目标词、提到其他型号、取值不同就删除|
|UNKNOWN|对象归属、条件关系、继承范围或分支不能可靠确定|默认匹配、默认冲突或强降位|

冲突不一定要求原文写出“仅适用”。例如明确标为某型号参数的独立表格行可有确定归属；但单纯提及另一型号不够。证据需展示为什么该事实属于该范围，而不是只返回一个词。

### 5.2 问题侧

- 用户明确表达的条件保留原文及位置；未表达不补全。
- 区分命名对象与属性值，不因某个复合词内部包含“样本”“定标”等词就额外创造阶段。
- 否定、猜测、引用、并列对象、条件式问法沿用现有强度/极性/role字段；归属不确定时不得升级为可淘汰硬条件。
- 同义词只在已验证、可配置的概念归一化内使用，不靠堆报警码词典。
- 问题解析若必须修改，只改变条件元数据；关键词、向量查询逐字保持基线不变，并做断言验证。

### 5.3 证据侧

优先使用原有句子、列表项、明确表格行和可追溯表头。没有可靠结构时，使用保守的局部文本范围；无法绑定就UNKNOWN，不假装恢复了PDF或PPT空间结构。

每条判断至少说明：

```json
{
  "condition_kind": "object / model / stage / scope / direction ...",
  "question_span": "原问题中的条件原文",
  "status": "match / conflict / unknown",
  "candidate_quote": "原资料中的依据；未知可以为空",
  "source_span": {"start": 0, "end": 0},
  "relation_basis": "正文 / 明确行列归属 / 已有章节归属 / 无法绑定",
  "reason_code": "same_fact_supported / same_fact_conflict / binding_unknown ...",
  "reason": "为什么该事实适用、不适用或无法确认"
}
```

上述为输出示意，字符偏移必须根据实际文本计算；不得以0填充假位置。不能定位时用null及原因。不要伪造0.95等精确置信度；规则确定性与模型概率须区分。

### 5.4 边界例子

|情形|预期|
|---|---|
|表格有条码尺寸，没有重复“样本”二字|对象范围UNKNOWN；不能因此整体后移|
|问题问电压偏高，正文温度偏低|不同属性，不判方向冲突|
|样本检测异常，处理步骤要求重新定标|操作步骤不等于故障阶段，不直接冲突|
|同一片段说明A、B型号的各自参数，用户问A|保留片段，限定目标分支；不把B参数当A参数|
|独立参数行明确归属B型号，用户只问A|有可靠排他归属时可判冲突；否则UNKNOWN|
|方法段同时讨论单项目、多项目，用户问多项目|包含目标分支时不得整段淘汰；无法确认分支时UNKNOWN|
|只出现另一个报警代码，但当前模块没有可靠的报警事实归属能力|记录限制；不声称已识别该冲突|

B可以复用字段和局部文本提取；不能默认沿用原有的“相反词出现就冲突”规则。未支持的关系保持UNKNOWN，并在真实错场景检查中报告未识别率，不能以少误删掩盖过滤失效。

### 5.5 为什么具备通用性

通用的是“对象—属性—值—条件—依据”的判断协议及冲突证明要求，不是声称少量规则能穷尽业务语言。报警、型号、阶段只是应用实例。规则不能可靠识别的关系要有unknown出口。

如果真实业务负例显示保守规则普遍不能识别冲突，下一轮再对这些关系做本地离线模型对照；本轮不同时换模型，避免归因不清。

## 6. 门禁与Context：第三个独立因素C

A/B验证后，专门统计：正确候选仍存在，却因`required_constraint_not_confirmed`或阶段竞争追问而无Context的题。

只有确有这类损失时，再独立验证C：

- 不将“没有候选明确确认条件”写成“候选与条件冲突”。
- 诊断和Context条目保留每个条件的UNKNOWN，并说明不能由此推断用户型号或扩大适用范围。
- 未确认范围的证据可作为有范围限定的资料参考；不等于已经足以作确定性回答。
- 只有确定缺失字段会改变具体答案时才考虑追问；方法分支问题不因未给具体案例数据就一律追问。
- 全部候选被证实冲突、确无合格证据时仍应保留无依据状态，不能为提高Context覆盖强行放行。

本轮只评API前结果；即使C保留了带限定的Context，也不能宣称最终答案已经遵守了范围。若C需要改变最终回答策略，另立生成验证，不在本轮顺便调用API。

Context最多新增简短、明确的条件元数据，不改变原始引文，不投射Gold，不增加多层后处理。元数据必须依据实际included_text；正文被预算截断后，不能保留只存在于被截掉部分的适用性证明。

## 8. 完整执行顺序

### 第一步：复现基线并建立问题清单

逐题列出BGE顺序、条件标签及依据、条件后顺序、门禁理由、实际Context。基线111/111需逐字复现窗口最高分结果，否则先排查接线和版本。

检查所有变差题和非Gold片段，不能只看已知条码题。记录入口缺失和重排缺失，不归到条件阶段。

### 第二步：只跑A

固定现有条件标签，取消条件再排序。统计恢复/丢失引文、排名变化、新增错误场景、最终门禁清空。

此时应能回答：高相关UNKNOWN被保留后，恢复多少必要证据？有没有挤走必要MATCH？有没有因为旧误判或门禁而仍失败？

### 第三步：开发B并跑完整2×2对照

|组别|判定|排序|
|---|---|---|
|基线|旧判定|旧排序|
|A|旧判定|保持BGE顺序|
|B|新局部判定|旧排序用于隔离归因|
|A+B|新局部判定|保持BGE顺序|

B组的旧排序只是实验控制，不是推荐结构。新判断若需要问题侧元数据，记录它是B内部的解析变化；上游检索表达式仍必须一致。

### 第四步：核验C是否必要

若C触发条件成立，至少比较A+B与A+B+C；若A单项也被旧门禁阻断，可增加A+C。不能直接覆盖A+B结果。保留首次失败，不按结果择优覆盖记录。

### 第五步：真实入口及独立验证

- 先用冻结上游候选完成全部111题，逐项断言只有允许的条件阶段和下游改变。
- 对最终候选方案再执行全部111题真实API前入口；检查召回/重排输入是否与基线一致。若索引漂移，单独记录，不能混为方案收益。
- 复用已有但未参与本轮调试的来源保留集，固定协议后只执行最终比较。由于该集合以前已经运行过，不能称完全未见过的全新验收集。
- 新增关系测试使用未参与调参的真实资料片段及人工可审的反事实对；冻结后不根据分数继续补词。新增标签全部pending。
- 检查原第49张多分支总结页、022等旧实验增删片段，即使它们不是Gold也必须检查误删。

### 第六步：交付和采用判断

生成原程序格式的`report.html`，各方案、各题、八阶段可切换，附实际Context对照及原资料页按钮。报告说明实验开关状态；未经采用，应用默认仍为当前已采用窗口最高分＋原条件检查。

如用户已授权根据结果采用，则只有满足门槛的最小方案接入；接入后再做默认构造器回放和真实入口一致性检查。不能以“建议下一轮”替代已经授权的验证工作。

## 9. 指标与人工复核

### 自动指标

- 条件前/后的Gold Recall@1、@3、@5、MRR及全部Gold保留率。
- 最终证据和实际Context的全部引文覆盖，逐题引文排名；仍按当前source-quote匹配，不能放宽页码。
- 条件导致的正确证据误删、误降位数量。
- 已标注真实冲突的识别率、误删率；分母写明是复核片段数，不能宣称覆盖所有错场景。
- 进入Context的标注负例数，新增/移出片段、去重与预算影响。
- UNKNOWN数量、原因、是否被清空；不以UNKNOWN变少作为性能目标。
- 在没有条件、没有冲突或短普通问题上，顺序/正文是否符合预期不变。

### 必须人工看原文的项目

所有被新增硬排除的片段；所有新增丢失Gold；所有新增标注负例；新增非Gold但疑似型号/对象/阶段干扰；多分支片段；正负同页混合；只有文件名提供范围的片段；部分正文进入Context的片段。

新增候选出现在报告不等于答案已误用；但它是已确认的输入变化，不能因为Gold没有变差就忽略。原文不足的关系标待裁决，不编造关系标签。

## 10. 采用门槛与阻断条件

1. 正式题无未经解释的新增Gold丢失，诊断/来源保留集的损失也需逐条说明；不能靠另一些题的收益抵消真实误删。
2. 原第49张等已确认多分支资料不得再整段误删。
3. 不出现新增、已确认不适用的证据被当作MATCH或无条件确定依据；UNKNOWN仍需显示未确认状态。
4. 若新增不适用片段，明确判断是旧检测缺口暴露、排序引入的入选变化还是新判定错误。不能笼统归因，也不能抹掉排序的独立收益；可分别采用A、阻断有问题的B。
5. 明确不相容的同对象/同属性真实负例要能被有效排除；如果只是全部变UNKNOWN以逃避误删，不算完成适用性修复。
6. 非条件模块的模型、候选、分数、Gold、发布索引及持久化设置保持冻结。
7. 单元、兼容和全部现有测试；当前544通过、10个既有失败是参考基线，失败名称需逐项核对，不宣称全绿。
8. 输出明确结论：共同原因、改动模块、收益题、退化题、未解决题、是否值得采用；不只报总体分数。

## 11. 本轮明确不承诺解决

- 019处理页在重排入口外、BS-800温度系数证据入口裁剪；需另外处理场景关系和入口候选，不让条件检查从Gold或全库偷偷补来源。
- BGE本身的语义偏好、数值推理和任意业务术语理解。
- 自动证明所有跨型号、跨报警资料适用；未知能力必须保留。
- 未调用API时，不宣称最终答案正确率、追问质量或拒答质量改善。

**最小推荐路线：先验证A，再验证B和A+B；仅在旧门禁确实阻断有效证据时单独验证C。** 每一步完成全量比较并记录得失，最终可只采用有独立收益的部分，不把全部改动捆绑成一次“大重构”。
