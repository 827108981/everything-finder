# 启动自动增量更新与后台搜索并发开发需求

## 1. 文档目的

本需求用于实现以下用户体验：

1. 用户已经选择的搜索目录在程序启动后自动检查新增、修改和删除文件。
2. 检查和解析全部在后台执行，主界面正常显示，用户可以立即进入搜索页面。
3. 首次全量索引尚未完成时，已完成并提交的文件可以被搜索；未完成文件不阻塞已有搜索结果。
4. 启动自动更新、文件监控、用户手动更新和首次索引不能互相重复启动或破坏索引一致性。
5. 无权限、被占用、正在复制或解析失败的文件不能中断整个索引，也不能通过大段错误弹窗制造“程序不可用”的感觉。
6. 在不降低 OCR 精度、不跳过应索引内容的前提下，降低首次索引和后台增量检查的实际耗时。

本需求不包含视频内容解析。视频继续按现有规则只保留文件元数据或排除状态。

## 2. 当前实现与问题

当前代码已经具备以下基础能力：

- 搜索范围启用/禁用状态。
- 文件监控和事件防抖入口：`local_full_text_search/core/file_monitor.py`。
- 增量判断所需的路径、大小、修改时间、快速指纹、内容指纹和解析器版本。
- 后台索引线程：`local_full_text_search/workers/scan_worker.py`。
- 多解析车道、任务恢复、批量写入和部分全文索引发布。
- SQLite WAL、写入超时和搜索可用性状态。

当前不足：

1. 文件监控事件只设置“检测到文件变化”状态，需要用户手动点击更新。
2. 程序启动后没有统一调度一次自动增量检查。
3. 文件监控事件与正在运行的首次索引之间没有明确的合并协议。
4. 搜索可用性、索引运行状态和自动更新状态需要进一步分离，避免索引运行时错误地禁用搜索。
5. 操作失败、目录不可访问或数据库短暂繁忙时，需要保证索引主流程继续运行。

### 2.1 启动界面与数据库快速路径整改

当前“本地全文搜索仍在启动，当前阶段：解析数据库位置，已等待 15 秒”的模态提示必须取消。该提示会阻止用户看到主界面，并制造应用已经启动失败的感受。

启动数据库定位必须采用以下顺序：

1. 优先读取用户配置中最后一次成功使用的数据库绝对路径。
2. 配置路径存在时执行轻量校验，只检查文件存在、SQLite 文件可打开、必要核心表可读，不在主线程执行完整迁移、完整性扫描或全文索引修复。
3. 轻量校验通过后立即显示主窗口，并使用该数据库加载已有搜索投影。
4. 完整数据库验证、结构迁移、遗留任务恢复和索引状态审计转移到后台线程。
5. 配置路径不存在或无法打开时，再检查受支持的默认位置和上次迁移位置。
6. 确实找不到可用数据库时，仍应先显示主界面，在页面内提供“重新选择数据库位置”“新建数据库”和“打开诊断目录”，不得使用启动等待弹窗阻塞应用。

禁止行为：

- 不得因为数据库验证超过固定秒数就弹出“仍在启动”模态窗口。
- 不得在主窗口显示前执行可能遍历大数据库或重建全文索引的操作。
- 不得在已经找到且能够读取数据库时反复搜索所有磁盘位置。
- 不得因为后台验证较慢而禁用整个应用；兼容的已提交搜索投影应继续可读。

状态展示要求：

- 主界面已经显示但后台验证未完成时，顶部显示轻量状态“正在检查索引数据库”。
- 如果数据库结构兼容，搜索立即可用。
- 如果必须迁移且旧结构无法安全读取，主界面仍保持响应，只在搜索区域显示“数据库正在升级”，并显示迁移阶段和进度。
- 只有数据库无法打开且所有恢复路径均失败时，才显示页面内错误状态；错误信息必须可读，不直接展示完整异常堆栈。

### 2.2 两类“更新”按钮的语义与文案

索引管理页顶部更新按钮和每个搜索范围卡片中的“更新”必须有不同且明确的作用，不得继续使用相同文案让用户猜测。

顶部操作：

- `更新全部范围`：使用普通模式更新所有已启用搜索范围。
- `性能模式更新全部`：使用性能模式更新所有已启用搜索范围。
- 索引正在运行且已经安全暂停时，以上两个按钮可以临时作为运行模式切换控件，但文案必须明确显示 `切换到普通模式` 和 `切换到性能模式`。
- 未进入安全暂停状态时，模式切换按钮不可用，并通过悬浮提示说明“完全暂停后可切换模式”。

搜索范围卡片操作：

- 卡片按钮改名为 `更新此范围`。
- 点击后只扫描该卡片对应的 `root_id`，不得连带扫描其他已启用范围。
- 当前范围更新时，其他范围已有搜索结果继续可用。
- 当前范围已经有任务运行时，重复点击不得创建第二个任务，只合并为该范围的一次后续增量更新请求。

交互要求：

- 每个更新按钮必须有悬浮提示，说明更新对象和所用模式。
- 任务状态中必须显示“正在更新全部范围”或“正在更新：目录名称”，不能只显示笼统的“正在更新”。
- 自动启动增量更新不能模拟点击某个界面按钮，应直接向统一调度器提交明确的范围集合。

### 2.3 未成功索引列表超过 2000 条的显示要求

当前未成功索引页面一次查询和渲染最多 2000 条，这只能作为单次加载保护值，不能作为用户可见的总数上限。

必须实现：

1. 标签页和标题显示数据库中的真实总数，例如 `阻断项 12,045`，不能显示当前加载的 2000 条作为总数。
2. 列表采用数据库分页或虚拟列表，禁止一次向 `QTableWidget` 加载全部记录。
3. 建议默认每页 200 条，允许配置为 100、200、500 条；显示当前页、总页数和总记录数。
4. 原因、格式、状态和搜索范围筛选必须在数据库查询层执行，并同步返回筛选后的真实总数。
5. 翻页、切换筛选和刷新时保持界面响应，不得因为统计或加载大量记录卡住主线程。
6. `导出明细` 默认导出当前筛选条件下的全部记录，不得只导出当前页；导出前说明记录数量。
7. 勾选必须区分“当前页已选”“当前筛选结果全部选中”，涉及排除、重试或删除索引记录时必须明确作用范围并二次确认。
8. 自动更新期间，真实总数允许变化；页面刷新后总数和列表必须来自同一查询条件，避免显示数量与内容不一致。

分页查询至少需要稳定排序键，例如“最后尝试时间倒序 + 文件 ID”，防止新增记录导致翻页重复或遗漏。

### 2.4 主进度固定为“完成数 / 总数”

所有索引阶段的主状态必须始终以 `已完成 X / Y` 为核心信息。`Y` 是当前已经发现且需要处理的文件总数，可以随着目录发现继续增长。

显示规则：

- 目录发现阶段：`已完成 0 / 256（仍在发现文件）`。
- 规划阶段：`已完成 12 / 2,304`。
- 解析阶段：`已完成 1,205 / 2,304`。
- 部分搜索可用：`已完成 1,205 / 2,304 · 已完成部分可搜索`。
- 任务结束：`已完成 2,280 / 2,304 · 失败 24`。

“正在读取指纹”“正在规划 105/111”“正在流水分析”等属于诊断信息，只能放在第二行、详情区域或悬浮提示中，不能替代主进度。

完成数必须只统计进入终态的文件，包括成功、仅元数据、明确跳过、人工排除和最终失败；正在处理和等待中的文件不得提前计入完成数。总数增长时进度条可以回退比例，但完成数本身不得倒退。

### 2.5 ETA 必须及时给出有效结果

界面不得长时间停留在没有参考价值的“正在估算”。ETA 必须区分目录发现、任务规划和实际解析三个阶段。

规则如下：

1. 目录发现或总数仍快速增长时不计算解析 ETA，显示 `正在统计文件`。
2. 进入实际解析后开始采样；至少运行 10 秒且至少 12 个文件进入终态后，才允许显示预计剩余时间。
3. 满足采样条件但模型仍不稳定时，显示 `暂无法可靠估算`，不得继续显示“正在估算”。
4. 从进入实际解析开始最多 30 秒必须结束“正在估算”状态，在“预计剩余约 N 分钟”或“暂无法可靠估算”之间选择一个。
5. 界面只显示单一平滑值，例如 `预计剩余约 18 分钟`，不显示跨度过大的范围。
6. ETA 使用各解析车道近期完成速度、历史中位数和指数平滑计算，不能简单用“已用时间 / 完成文件数”推算所有文件。
7. ETA 最快每 10 秒更新一次，单次跳变超过前值的 25% 或 30 秒时应继续平滑，避免频繁抖动。
8. 暂停期间 ETA 冻结；恢复后重新采样，不把暂停时间计入处理速度。
9. 总数变化、解析车道切换或进入大型 OCR/ZIP 文件时允许重新评估，但不得重新长时间显示“正在估算”。

内部可以保留置信区间和样本数用于日志诊断，界面不显示宽范围。

### 2.6 耗时控件操作的二层进行中窗口

暂停、取消、删除搜索范围、批量排除、批量恢复、数据库迁移和全文索引重建等操作如果不能立即完成，必须使用二层进行中窗口或等价的应用内遮罩，明确告诉用户程序仍在工作。

显示时机和行为：

- 操作在 300 毫秒内完成时不显示窗口，避免闪烁。
- 超过 300 毫秒显示操作名称、当前阶段、已用时间和可确定的进度。
- 窗口必须持续处理界面事件，能够拖动主窗口、重绘和响应允许的取消操作，不能出现 Windows“未响应”。
- 后台任务至少每 1 秒发送一次心跳；无数值进度时显示动画和明确阶段，不能使用静止界面。
- 涉及数据库提交的不可取消阶段，应将取消按钮改为“正在完成安全提交”，不能强行终止并破坏数据。

典型文案：

- `正在安全暂停：等待 2 个活动任务到达安全检查点`
- `正在删除搜索范围：已清理 3,200 / 12,000 条索引记录`
- `正在取消：正在保存当前页解析进度`
- `正在切换模式：正在重建解析进程池`

删除搜索范围必须按照“确认删除 → 安全暂停相关任务 → 停止该范围后续提交 → 后台分批清理数据库 → 刷新搜索投影 → 显示完成结果”的顺序执行。不得在界面线程中直接删除大量数据库记录，也不得在该范围仍被索引时并发删除。

## 3. 功能范围

### 3.1 自动更新对象

- 只处理已启用的搜索范围。
- 禁用的搜索范围不得被启动自动更新、文件监控回调或后续补偿任务重新加入。
- 搜索范围不存在时记录状态并跳过，不弹窗阻塞其他范围。
- 多个范围可以进入同一个自动更新任务，但应按现有索引调度策略逐范围处理。

### 3.2 启动时机

程序启动必须按以下顺序执行：

1. 解析数据库位置并确认数据库可打开。
2. 主窗口显示，搜索页面和索引管理页面可操作。
3. 完成必要的数据库迁移或明确进入“数据库准备中”状态。
4. 数据库可写、索引状态可读后，由统一更新调度器提交一次启动自动增量任务。
5. 自动更新在后台线程执行，不得阻塞窗口消息循环。

数据库不存在、迁移失败或无法获得数据库锁时，不得启动自动解析任务；应在界面内显示原因并保留已有数据库，不得用启动阶段的模态错误弹窗阻塞用户。

### 3.3 手动更新与自动更新统一调度

启动自动更新、文件监控触发更新和用户点击“更新”必须进入同一个调度器，不允许分别创建独立扫描线程。

调度器至少需要维护以下状态：

- `idle`：没有更新任务。
- `scheduled`：已经收到更新请求，等待防抖或数据库就绪。
- `running`：正在执行扫描或解析。
- `pause_requested` / `paused`：等待安全检查点或已安全暂停。
- `cancel_requested`：正在安全取消。
- `completed`：本次任务完成。
- `failed`：任务自身发生基础设施错误，但已保存可恢复进度。

如果已有任务处于 `running`：

- 新的自动更新请求不得再创建第二个索引线程。
- 只记录待处理的范围、路径和变更代次。
- 当前任务结束后，统一调度器根据变更代次决定是否补跑一次增量检查。
- 多次事件必须合并为一次后续任务。

## 4. 增量检查规则

### 4.1 目录扫描是必要的

启动时必须重新读取已启用目录的文件清单，才能可靠发现新增和删除文件。这里的“增量”指：

- 目录清单可以重新扫描；
- 未变化且已成功的文件不重新解析；
- 只对新增、修改、删除、未完成或解析器版本不匹配的文件执行后续处理。

不得为了避免目录扫描而直接相信上次监控事件，因为程序关闭期间可能丢失文件系统事件。

### 4.2 文件状态判断

对已有文件按以下优先级判断：

1. 路径和文件类型是否仍然存在。
2. 文件大小、修改时间和快速指纹是否变化。
3. 解析器名称和解析器版本是否匹配当前版本。
4. 文件当前解析状态是否为成功、仅元数据、待处理、失败或已取消。
5. 对需要确认的文件再执行内容指纹或完整哈希，避免对所有文件重复读取全文。

判定为未变化且解析成功的文件不得重新创建解析任务。

### 4.3 正在写入的文件

新文件或发生变化的文件必须先通过稳定性检查：

- 连续两次读取的大小和修改时间一致；
- 检查间隔可配置，默认 1 至 3 秒；
- 文件被其他程序锁定时进入延迟重试，不立即记为永久失败；
- 超过重试次数后记录为“暂不可访问”，留在未成功索引中。

解析完成提交前再次确认源文件指纹。如果解析期间文件发生变化，旧结果不得覆盖新文件状态，应丢弃或标记为过期并重新排队。

### 4.4 删除和重命名

- 本次目录清单中不存在、但数据库中仍存在的文件标记为删除，并清理对应全文块和搜索结果。
- 重命名是否作为删除加新增，或通过内容指纹复用旧文档，需要在实现中统一，不能产生重复结果。
- ZIP 容器变化时必须重新检查成员清单；未变化的成员可复用已有结果。

## 5. 首次索引未完成时的搜索并发

### 5.1 搜索可用原则

搜索权限不应绑定“全部文件是否已经完成”。应区分：

- `index_complete`：全部应处理文件均已完成，全文索引最终一致。
- `search_available`：当前已有可查询的已提交全文索引。
- `search_is_partial`：搜索可用，但仍有文件在后台处理。

只要存在已提交且一致的搜索投影，搜索页面必须保持可用，即使 `active_runs > 0` 或仍有待处理文件。

首次索引时，如果还没有任何可提交的内容：

- 搜索输入框和页面仍然可以打开；
- 查询可以显示“索引正在建立，当前暂无可用结果”；
- 第一批文件成功提交后，自动切换为部分搜索；
- 不得因为后台仍在索引而反复禁用和启用搜索控件。

搜索结果必须明确这是当前已完成部分，不能声称覆盖尚未完成的文件。

### 5.2 数据一致性

搜索线程只能读取已提交的稳定索引版本。后台更新期间：

- 新解析结果先写入任务结果和候选投影；
- 候选投影通过原子发布后才对搜索可见；
- 发布失败时继续使用上一版可搜索投影；
- `content_fts_dirty` 或候选版本未通过发布门禁时，不得向搜索暴露不完整候选数据；
- 删除文件和替换文件的全文块必须与文件状态在同一事务或可恢复提交边界内更新。

搜索可以短暂看到更新前的旧结果，但不能看到半条内容、重复文件或已提交文件缺少必要元数据的结果。

### 5.3 SQLite 并发

- 保持 WAL 模式。
- 搜索使用独立只读连接或短事务。
- 索引写入保持单写入者，解析进程不得直接写数据库。
- 遇到数据库短暂锁定时按退避策略重试，不得让搜索线程或索引主线程直接失败。
- 全文索引重建、候选发布等重量操作必须有明确的发布状态，不能在搜索连接中进行破坏性清空后长时间等待。

## 6. 文件监控与首次索引的冲突处理

### 6.1 事件只作为提示，不作为最终事实

文件监控事件用于记录“某范围发生变化”，不直接在回调线程解析文件。最终变更以后台增量扫描重新读取目录和指纹为准。

### 6.2 首次索引运行期间

当首次全量索引或其他索引任务正在运行时：

1. 监控事件只追加到待处理集合，不启动第二个扫描任务。
2. 待处理集合至少按 `root_id` 去重，并保留最新变更代次。
3. 当前扫描发现并处理了该文件时，可以清除对应待处理标记。
4. 当前扫描结束后，如果期间仍有未确认的变更代次，自动执行一次补偿增量扫描。
5. 补偿任务也必须使用同一个调度器，不能递归创建任务。

### 6.3 文件在解析中发生变化

- 解析任务开始时记录源文件指纹。
- 解析结果提交前校验指纹。
- 指纹变化则不提交旧内容为最终结果，任务转为待重试。
- 多次快速变化时采用防抖和最大重试间隔，避免单个文件占用解析队列。

### 6.4 用户操作冲突

- 暂停：自动更新和首次索引使用同一安全暂停协议。
- 取消：停止提交新任务，保留已提交结果和可恢复检查点。
- 删除搜索范围：不得与扫描同时直接删除数据库记录；应先安全暂停或将删除请求排队，删除完成后重新计算启用范围。
- 禁用搜索范围：立即阻止该范围新的扫描任务，但不应删除已有数据，除非用户明确执行删除范围操作。

## 7. 用户界面要求

### 7.1 无感后台运行

启动自动更新不得弹出确认框或阻塞式窗口。主界面顶部使用轻量状态提示，例如：

- `后台检查文件变化`
- `自动增量更新：已完成 120 / 380`
- `已有搜索结果，后台仍在更新`

搜索页保持可进入和可查询。

### 7.2 进行中状态

暂停、取消、删除范围、数据库清理等可能耗时的用户操作可以使用二层进行中窗口，但必须：

- 显示操作名称、当前阶段、已用时间和可确定的进度；
- 明确说明正在等待安全检查点，而不是显示为无响应；
- 界面线程不执行数据库清理或目录遍历；
- 操作完成后自动关闭，并显示结果；
- 自动更新不使用模态窗口，避免打断用户搜索。

### 7.3 进度和 ETA

自动更新的主进度始终显示“完成数 / 当前已知总数”。目录仍在发现时，总数可以增长。

ETA 规则：

- 样本不足时显示“正在收集速度”或“暂不可估算”，不能长时间显示无意义的“正在估算”；
- 有稳定样本后显示单一预计剩余时间，不显示过宽范围；
- 搜索、自动更新和首次索引同时存在时，状态文案不得互相覆盖；
- 详细当前文件、解析车道和无进展诊断放入悬浮提示或二级详情。

## 8. 异常与恢复要求

以下情况不得中断其他文件或其他搜索范围：

- 单个文件无权限；
- 文件正在被占用；
- 路径在扫描过程中消失；
- PDF、Office、ZIP 或 OCR 子进程失败；
- 数据库短暂锁定；
- 文件监控库不可用；
- 单个解析任务无进展并被看门狗回收。

每个异常文件必须保留：路径、解析阶段、错误分类、重试次数、最近一次尝试时间和恢复建议。后台自动更新只在状态区汇总失败数，不能弹出一个错误窗口导致索引流程中断。

程序异常退出后再次启动时：

- 恢复未完成的任务和临时结果；
- 不重复解析已安全提交的文件；
- 对启动期间发生变化的文件重新进行稳定性检查；
- 自动更新仍只创建一个任务。

## 9. 配置要求

建议提供以下配置：

- `startup_incremental_update_enabled`：是否启用启动自动增量更新，默认开启；
- `monitor_file_changes`：是否监听运行期间文件变化；
- `startup_update_delay_seconds`：主界面显示后的启动延迟，默认 1 至 3 秒；
- `file_stability_check_seconds`：文件稳定性检查间隔；
- `file_stability_retry_limit`：文件稳定性最大重试次数；
- `change_event_debounce_seconds`：文件监控事件合并时间；
- `auto_update_retry_delay_seconds`：补偿增量任务的最小间隔。

配置变更必须在下一次调度任务生效，不得中途破坏当前解析任务。

## 10. 索引耗时瓶颈与优化方案

### 10.1 当前实测基线与判断原则

最近一次可完整分析的 2,346 文件增量运行数据如下：

| 指标 | 耗时 |
|---|---:|
| 总墙钟时间 | 220.6 秒 |
| 目录扫描 | 60.2 秒 |
| 指纹和哈希 | 114.5 秒 |
| 解析累计时间 | 139.5 秒 |
| 其中 OCR | 137.5 秒 |
| 数据库写入 | 3.6 秒 |
| 全文索引最终构建 | 0 秒 |

各解析车道、扫描、指纹和写入存在流水并发，阶段耗时不能直接相加。优化判断必须同时记录总墙钟时间和关键车道时间，不能用累计 CPU 时间代替用户实际等待时间。

其他已确认现场数据：

- 6,404 文件运行总耗时约 5,805 秒，其中指纹和哈希约 5,196 秒，说明大目录、ZIP 成员和重复候选的读取会成为绝对瓶颈。
- 1,999 文件运行总耗时约 947 秒，OCR 车道累计约 1,175 秒，数据库写入累计约 332 秒。
- 未变化的 331 文件、约 17.2 GiB 目录增量复扫约 7 至 10 秒，说明普通未变化文件复用有效，文件总字节数本身不是唯一瓶颈。
- 日志出现过单批 SQLite 写入 5 至 171 秒以及 `database is locked`，说明部分搜索实时更新全文索引时，数据库写入可能从次要开销变为主瓶颈。

本章优化必须遵循：

- 不通过降低 OCR 检测边长、降低识别置信度、减少原图文字区域、跳过分块兜底或截断正文换取速度。
- 不跳过大文件、ZIP 成员、旧版 Office 或扫描 PDF。
- 不关闭索引期间的部分搜索能力来掩盖数据库性能问题。
- 不扩大并发到超过内存和 CPU 预算，避免系统失去响应。
- 所有优化必须保持搜索命中、正文块、来源路径、失败清单和人工排除语义一致。

### 10.2 OCR 关键路径优化

OCR 是当前新增图片和扫描 PDF 的主要解析瓶颈。应实施以下优化：

#### 10.2.1 OCR 进程和模型常驻

- OCR 进程池从“每个搜索范围创建一次”提升为“单次索引运行共享”，不同搜索范围不得重复加载同一模型。
- 启动自动增量任务结束后允许保留 OCR 进程一段可配置的空闲时间，默认建议 3 至 5 分钟；空闲超时后正常退出释放内存。
- 模型只在第一个 OCR 任务到来时延迟加载，普通增量扫描不能仅因为启用了 OCR 就加载模型。
- 模型加载失败只能影响 OCR 车道，其他文件继续索引。
- 模型进程回收、模式切换和应用退出必须有明确的 PID 注册与清理验证，不能产生残留进程。

#### 10.2.2 模型和配置指纹

- OCR 缓存键必须包含源内容摘要、图片解析器版本、OCR 模型指纹、检测配置、识别配置和语言。
- 模型文件指纹在安装包或首次验证时计算一次并持久化，不得每张图片重新读取全部模型文件计算摘要。
- 模型文件大小、修改时间和发行清单未变化时直接复用已验证指纹。
- OCR 配置变化只使相关 OCR 缓存失效，不得强制普通文本、Office 或原生 PDF 重新解析。

#### 10.2.3 OCR 调度和微批处理

- 平衡模式至少保证 1 个有效 OCR worker；性能模式在内存允许时使用 2 个有效 OCR worker。
- 指标必须统计“配置 worker 数”和“实际执行过任务的 worker 数”，发现配置为 2 但长期只有 1 个实际 worker 时记录调度告警。
- 不同图片或不同 PDF 页可以并行；同一超大图片的分块并发必须受像素和内存预算限制。
- 检测和识别微批等待时间不得混入推理时间。微批等待采用毫秒级上限，默认 30 至 100 毫秒；P95 超过 250 毫秒时记录诊断。
- 不得为了凑批次让单张图片等待数秒。任务不足时应立即执行小批次。

#### 10.2.4 保持识别质量的分流

- 图片继续使用“960 检测 + 原图文字区域识别 + 低质量时原图分块”策略。
- PDF 优先提取原生文字，仅将无有效文字、原生文字明显不足或明确需要补充的页面送入 OCR。
- OCR 页面和图片必须先查询内容缓存；相同原始字节在不同路径或 ZIP 成员中只 OCR 一次。
- 低质量分块兜底只在质量门禁触发时执行，已由原图区域可靠识别的内容不得重复进入整图分块。
- OCR 每完成一个区域、分块或页面都要保存语义进展和检查点，暂停、回收或异常后从最近安全点继续。

### 10.3 目录扫描、指纹和完整哈希优化

#### 10.3.1 持久化目录快照

- 为每个搜索范围保存最近一次完整对账代次，包括路径、大小、修改时间、文件标识、快速指纹和解析器版本。
- 启动增量检查先批量读取目录元数据，与快照对比；元数据和解析器版本均未变化的成功文件不打开正文。
- 文件监控事件只缩小优先检查范围，启动时仍需完成目录对账，防止程序关闭期间丢失事件。
- 重叠搜索范围中的同一路径只读取一次元数据，并在数据库中正确关联不同范围。

#### 10.3.2 单次读取流水线

- 对确实需要读取内容的文件，将复制到 spool、完整 SHA-256、格式预检和解析输入合并为一次顺序读取，避免同一大文件反复打开。
- 已有可靠完整摘要且源文件快速指纹未变化时复用摘要。
- 抽样指纹只用于候选筛选，只有去重或一致性协议明确要求时才补算完整 SHA-256。
- 同一来源在一次运行中只能有一个完整哈希任务；其他需要该摘要的任务等待并复用同一个结果，不得重复读取。
- 完整摘要必须持久化并绑定源文件大小、修改时间、快速指纹和解析器版本；这些条件未变化时，后续运行直接复用摘要。
- 指纹任务必须按介质和文件类型批量提交。SSD 可以使用有界并行，HDD、网络盘和可移动盘默认串行或低并发，避免随机读取反而降低吞吐。
- 读取失败、文件变化或取消时不得提交半成品摘要；临时 spool 必须可识别、可清理、可恢复。

#### 10.3.3 批量规划和数据库访问

- 目录枚举、文件状态读取和数据库已有记录查询必须批量进行，避免每个文件一次数据库查询。
- `planning_discovery_batch_size` 应根据目录介质和文件数量自适应，但必须有内存上限。
- 规划 worker 的进展以目录批次、文件状态批次、哈希字节数和 ZIP 成员数为语义单位。
- 单个文件规划失败只生成该文件的失败记录，不能回滚整个批次。

### 10.4 ZIP 规划与成员去重优化

- 外层 ZIP 的大小、修改时间和中央目录指纹未变化时，直接复用上一轮成员清单，不得重新逐成员规划。
- ZIP 中央目录指纹应基于规范化成员路径、CRC、压缩大小、解压大小和稳定成员序号，不读取每个成员正文。
- 外层 ZIP 发生变化时，先比较新旧成员清单，只为新增或变化成员创建任务，保留未变化成员正文和来源关联。
- 只有扩展名、大小、CRC 和解析器版本形成重复候选时，才读取成员正文计算完整摘要；不得为全部成员预先计算 SHA-256。
- 同一 ZIP 内、不同 ZIP 之间以及 ZIP 成员与普通文件之间的相同内容只解析一次，但每个真实来源都必须可以单独搜索和定位。
- 超过成员数、解压量或嵌套深度安全限制的 ZIP，应一次性生成明确状态并停止深入规划，不得在同一次任务中反复回退并重新打开。
- ZIP 成员按格式分配到普通、PDF、Office、OCR、旧版 Office 等全局车道；外层 ZIP 不得串行承担全部成员解析。
- 同一外层 ZIP 在一次运行中只能规划一次；取消、补偿扫描或其他范围引用同一来源时必须复用已完成的中央目录结果。
- ZIP 候选去重必须先使用成员路径、扩展名、大小、CRC和解析器版本筛选；没有候选时禁止读取成员正文计算完整哈希。

### 10.5 数据库写入与部分搜索发布优化

#### 10.5.1 单写入者和批量提交

- 所有解析进程只返回结果，不直接写 SQLite；保持单一 `IndexWriter`。
- 正文块、文件状态、任务终态和来源关联按大小、块数和最大等待时间组成批次。
- 状态心跳和“正在运行”标志使用短事务或尽力写入，不能与正文提交争夺长事务锁并中断索引。
- 每个写入批次记录等待时间、事务时间、块数、字节数和 FTS 更新时间。

#### 10.5.2 部分搜索增量发布

- 部分搜索继续保留，但不得对每个小文件立即执行高成本 FTS 删除和重建。
- 新结果先进入稳定正文表和待发布代次，按时间或文件数形成发布批次；建议最多间隔 1 至 3 秒，使搜索及时看到新结果。
- 发布过程必须原子切换；发布失败继续使用上一版可搜索投影。
- 增量删除全文行时使用与正文块主键一致的 `rowid` 精确删除，不允许按未索引列扫描整个 FTS 表。
- 全量重建时保留旧可搜索投影，候选 FTS 完成并通过门禁后再原子替换。

#### 10.5.3 锁竞争与慢批次治理

- SQLite 保持 WAL；搜索使用短只读事务，不得长期持有读快照。
- 写锁短暂繁忙时采用有界退避重试，不得因一次 `database is locked` 终止整个搜索范围。
- 慢于 2 秒的写入批次记录告警和阶段指标；慢于 10 秒时触发诊断快照，但不弹窗。
- 诊断至少包含活动连接数、等待锁时间、WAL 大小、批次块数、正在执行的索引操作和最近一次成功提交时间。
- 禁止出现数十秒到数分钟的单批 FTS 更新；若批次超限，应缩小批次或延后候选发布。

### 10.6 解析车道和长尾文件优化

#### 10.6.1 全局共享车道

- 一次“更新全部范围”应创建一组全局解析车道并在所有范围间复用，不能每切换一个搜索范围就销毁和重建全部进程池。
- 各范围可以顺序完成目录对账，但已规划任务应进入全局车道，避免后续范围等待前一范围所有长任务结束后才开始。
- 调度器必须记录任务所属 `root_id`，保证暂停、禁用和删除范围能够停止对应任务而不影响其他范围。

#### 10.6.2 关键路径调度

- 任务按预计成本使用“长任务尽早启动 + 短任务保持响应”的公平策略，避免所有小文件完成后只剩一个超大文件。
- 普通、PDF、OCR、ZIP、Office 和旧版 Office 独立限流，并共享全局 CPU、内存和磁盘预算。
- 性能模式应优先提高实际关键车道并发，而不是简单增加所有 worker。
- 当只有一个车道剩余且系统资源充足时，可在安全范围内临时提高该车道并发；恢复混合负载后自动回落。

#### 10.6.3 大文件专项

- 原生 PDF 按页任务图并行；扫描页单独进入 OCR，不能让整份混合 PDF 串行走 OCR。
- 大型 XLSX 使用流式 XML、共享字符串磁盘模式、sheet 预扫描和安全的 sheet 级并发，并保存 sheet/row 检查点。
- DOCX/PPTX 保持流式解析和文件级并发，不将整个压缩包一次性展开到内存。
- 旧版 DOC/XLS/PPT 保持 Word、Excel、PowerPoint 独立车道；转换缓存键包含源摘要、转换器类型和版本。
- 外部 Office/WPS/LibreOffice 子进程必须有无进展监控和 PID 精确回收，单文件失败不能阻塞车道。

### 10.7 启动自动增量更新的性能约束

- 自动更新不得每次启动都对未变化普通文件执行完整哈希或内容解析。
- 目录对账和指纹读取在后台执行，搜索请求具有更高交互优先级；用户搜索时自动降低后台磁盘和 CPU 压力。
- 自动更新期间产生的新监控事件只合并为一次补偿任务，不能不断重启扫描。
- 已知无变化的大型发行 ZIP、OCR 图片和 Office 文件必须直接复用已有成功结果。
- 自动更新的性能指标应按搜索范围分别记录，便于识别哪个目录长期占用时间。
- 默认平衡模式以不影响前台搜索和办公使用为目标；性能模式才允许使用更高 CPU 和内存预算。

### 10.8 性能验收门槛

在同一机器、同一数据库副本、相同语料和相同 OCR 配置下进行冷/热对比。所有耗时门槛必须同时通过结果一致性检查。

#### 10.8.1 正确性门槛

- 文件总数、成功数、仅元数据数、失败数、人工排除数一致。
- 搜索正文块数和关键查询命中不减少。
- OCR 文本量、关键关键词命中和平均置信度不得因性能优化显著下降。
- ZIP 每个来源路径、PDF 页码、PPT 页码、Excel sheet/row 定位保持一致。
- 数据库 `quick_check`、外键检查和候选发布门禁全部通过。

#### 10.8.2 性能门槛

- 未变化的 331 文件真实目录热复扫不得比当前 7 至 10 秒基线回退超过 10%。
- 数千文件的未变化目录不得重新产生解析任务；指纹和规划耗时相对当前基线至少降低 30%。
- 外层 ZIP 未变化时不得重新读取全部成员正文，相关完整哈希字节数应接近 0。
- 指纹、完整哈希和直接解析应按端到端收益选择，目标是缩短“索引完成时间”和“搜索可用时间”中的关键路径，而不是固定偏向某一种手段。
- 同一语料应分别记录“复用已有摘要、补算完整哈希后去重、直接独立解析”三种策略的总墙钟时间、搜索可用时间和资源占用；连续三轮中位数回退超过 5% 才判定策略选择需要调整。
- 去重后的搜索查询 P95 不得比未去重基准回退超过 10%或增加 100 毫秒，取更宽松者。
- OCR 模型在同一应用进程和同一配置下每个 worker 只加载一次，不因切换搜索范围重复加载。
- 性能模式配置 2 个 OCR worker且存在足够独立任务时，必须观察到 2 个 worker 实际完成任务。
- 数据库写入批次 P95 小于 2 秒，单批不得超过 10 秒，`database is locked` 导致整轮失败次数必须为 0。
- 增量结果发布后 3 秒内应可被新搜索查询到；发布期间旧索引持续可用。
- 搜索请求不能等待后台增量任务完成；后台运行时搜索 P95 延迟不得比空闲基线回退超过 50%或增加超过 1秒，取更宽松者。
- 动态策略比较的决策耗时必须计入总墙钟时间；批次决策开销目标不超过该批次预计解析/哈希时间的 1%，小批次不超过 50 毫秒。
- 探索采样不得导致同一文件重复完整哈希或重复解析；探索带来的额外读取、哈希、解析和等待时间必须单独列出。
- 性能模式下存在充足可并行任务时，应证明关键车道有实际并行收益；仅增加进程数但总时间无改善不能通过验收。

#### 10.8.3 必测语料

- 已有真实免疫资料目录。
- 包含数千图片和聊天记录的目录。
- 两个数百 MiB 发行 ZIP 及其未变化增量复扫。
- 纯原生 PDF、混合 PDF、纯扫描 PDF。
- 大型 XLSX、DOCX/PPTX 和旧版 DOC/XLS/PPT。
- 重复普通文件、重复 ZIP 成员及 ZIP 与普通文件交叉重复。
- 文件正在复制、文件被占用、无权限目录、扫描中修改文件和删除文件场景。

性能报告必须列出总墙钟时间、目录扫描、指纹、各解析车道、数据库等待/写入、FTS 发布、模型加载、峰值内存和实际 worker 使用情况。

### 10.9 去重、指纹与解析的自适应收益决策

去重、指纹确认和直接解析都是可用的优化路径。实现不能预先假定“必须去重”或“哈希一定不划算”，而应以端到端结果为准：在保证正确性和搜索完整性的前提下，选择能更快完成索引、让搜索更早可用且资源占用更低的路径。优化目标同时覆盖两类成本：减少不必要的解析，以及减少不必要的指纹和完整哈希。

#### 10.9.1 分层候选与策略比较

1. 先使用文件类型、原始大小、解析器版本、已有快速指纹，以及 ZIP 成员可用的 CRC 建立低成本候选集合。
2. 有候选且数据库已经保存可靠完整摘要时直接比较摘要，不重新读取源文件；这是最高优先级的低成本路径。
3. 没有候选时，默认不为跨来源去重额外补算完整 SHA-256，但如果该类型的历史数据表明“批量哈希后可以显著减少昂贵解析”，允许进入候选哈希路径。
4. 有候选但缺少完整摘要时，至少比较三种预计成本：直接独立解析、补算完整哈希后复用解析结果、等待或复用正在运行的共享哈希任务。
5. 成本模型必须纳入文件大小、介质类型、当前磁盘队列、解析车道排队、预计可避免的解析数量、缓存命中率、内存压力和搜索发布延迟。
6. 动态比较必须是轻量预测，不能为比较目的对同一文件实际执行两次哈希或两次解析。策略选择应按“文件类型 × 介质 × 大小区间 × 重复率”形成批次决策，不能为每个文件重新构建完整模型。
7. 冷启动或模型置信度不足时，只对有代表性的少量任务进行探索采样；其余任务沿用批次策略。探索采样的额外读取、哈希或解析必须单独计量，并设置上限。
8. 选择预计端到端成本最低的策略。固定倍率（例如 `预计解析时间 >= 完整哈希时间 × 1.5`）只能作为冷启动初始参数，不能作为硬门禁；运行中必须根据真实耗时修正。
9. 某次判断不划算时只影响当前候选批次，不得永久关闭该类型的去重或哈希；后续在硬件、负载、缓存命中率或解析器版本变化后重新评估。

OCR、扫描 PDF、旧版 Office 等解析成本高的内容可能更适合先哈希确认，但在磁盘拥塞或候选稀疏时也可能直接解析更快；普通 TXT、小型结构化文件通常解析更快，但若已有摘要或同批次重复度很高，也应优先复用摘要。最终以历史车道指标和当前负载共同决定。

#### 10.9.2 哈希结果复用

- 同一文件、同一 ZIP 成员和同一内容候选在一次运行中只能读取并计算一次完整摘要。
- 后续任务通过共享 future、任务 ID 或摘要仓库复用结果，不得各自重新提交哈希进程。
- 已成功提交的完整摘要跨运行持久化；快速指纹、大小和修改时间未变化时直接复用。
- 文件在哈希过程中变化时摘要作废并延迟重试，不能反复立即读取变化中的文件。
- 取消后恢复任务时优先读取已校验 spool 和摘要，不得从头重新哈希。

#### 10.9.3 ZIP 去重成本控制

- ZIP 外层未变化时，成员清单、成员候选和已有成员摘要全部复用。
- ZIP 外层变化时只处理新增或变化成员，未变化成员不能重新规划和哈希。
- 同一成员同时命中多个候选时只计算一次摘要，再与候选摘要集合比较。
- ZIP 成员读取、解压、spool 和 SHA-256必须采用一次数据流，禁止“为哈希解压一次、为解析再解压一次”。
- 发现候选摘要不一致后立即结束该候选比较，不进行无收益的额外重复读取。

#### 10.9.4 收益指标和动态策略切换

每轮索引必须记录：

- `dedup_candidate_count`：低成本候选数；
- `dedup_full_hash_count`：为去重补算完整摘要的数量；
- `dedup_hash_ms`：去重补充哈希耗时；
- `dedup_hash_bytes`：为去重额外读取的字节数；
- `dedup_parse_avoided_count`：避免解析数量；
- `dedup_parse_ms_avoided_estimate`：预计避免的解析耗时；
- `dedup_net_saved_ms`：采用去重路径相对直接独立解析路径节省的预计时间；
- `fingerprint_strategy`：本批次采用的策略（复用摘要、批量完整哈希、直接解析或混合）；
- `strategy_total_wall_ms`：策略对应的端到端墙钟时间；
- `strategy_search_ready_ms`：策略对应的首次可搜索时间；
- `strategy_resource_cost`：策略对应的 CPU、磁盘读取、峰值内存和进程占用；
- `strategy_decision_ms`：策略预测、候选分组和调度决策耗时；
- `strategy_exploration_overhead_ms`：探索采样相对批次基线增加的耗时；
- `dedup_search_p95_delta_ms`：去重前后搜索 P95 差值。

如果某种文件类型或来源组合连续两轮采用同一策略都没有收益，调度器应切换到候选策略重新比较，而不是简单永久关闭去重或永久强制解析。策略切换必须：

- 保留快速指纹和文件变化检测；
- 保留已计算的完整摘要、解析缓存和 ZIP 成员清单；
- 记录切换前后的索引总时间、搜索可用时间和资源占用；
- 将策略决策和探索采样开销纳入总成本；如果动态比较本身抵消了优化收益，应降低探索比例、扩大批次复用范围或直接沿用当前最优策略；
- 在解析器版本、硬件、介质类型、文件重复率或历史成本模型明显变化后重新采样；
- 只有当所有候选策略都无法带来收益时，才退回最简单的直接解析路径。

#### 10.9.5 动态比较开销门禁

- 策略预测默认只允许使用已存在的元数据、快速指纹、历史车道耗时和当前队列状态，不得因为“比较”额外打开正文。
- `strategy_decision_ms` 必须按批次累计，目标不超过该批次预计解析/哈希墙钟时间的 1%；对极小批次采用绝对上限，建议不超过 50 毫秒。
- `strategy_exploration_overhead_ms` 必须计入索引总墙钟时间和搜索可用时间；探索采样连续两轮未改善时自动减少采样比例，不能无限试错。
- 策略模型、批次分组和历史速度应缓存并带版本号；同一运行、同一类型和介质条件下复用决策，避免每个文件重复计算。
- 当决策服务异常、历史样本不足或开销门禁超限时，回退到预先验证的批次策略，不得阻塞索引或弹窗。

#### 10.9.6 搜索性能保护

- 去重只共享规范正文，不得丢失任一实际文件路径或 ZIP 内部路径。
- 搜索先命中规范正文，再通过有索引的来源关联表展开真实来源，禁止对每条结果执行 N+1 查询。
- 来源关联表必须具备 `document_id`、`root_id`、`container_file_id` 和活动状态所需索引。
- 同内容来源很多时仍受分页和最大结果数控制，不能一次展开全部来源阻塞查询。
- 去重关闭或自动降级时，搜索结果语义保持一致，只允许底层正文存储方式不同。

### 10.10 实施优先级

索引稳定性问题仍属于发行硬门禁，但性能优化必须严格按以下顺序实施和验证：

1. **P0：减少重复完整哈希和 ZIP 成员重复规划。** 建立单运行哈希任务去重、ZIP 中央目录复用和变化成员差异规划。
2. **P0：让指纹任务批量化并复用已有完整摘要。** 持久化摘要，合并读取、哈希和 spool 流程，并按介质控制并发。
3. **P0：OCR 进程跨搜索范围常驻。** 避免每个范围重复加载模型，并验证配置 worker 数等于实际有效 worker 数。
4. **P1：提高普通模式的自适应并发。** 根据 CPU、内存、磁盘类型和前台搜索压力动态调整普通、PDF、ZIP、Office 与 OCR 车道，不能静态无限增加进程。
5. **并行硬门禁：数据库慢批次和锁竞争治理。** 任何阶段不得因 `database is locked` 或分钟级写入中断整轮索引。
6. **P1：全局跨范围解析车道和长尾公平调度。** 减少重复建池和最后几个文件拖尾。
7. **P1：PDF、XLSX、ZIP 和旧版 Office 大文件专项优化。** 在不降低准确性的前提下增加安全并行和检查点。
8. **P2：根据历史车道数据自动调整并发和 ETA。** 在核心正确性和稳定性完成后实施。

## 11. 验收标准

### 11.1 启动自动更新

- 已有数据库和已启用目录时，程序显示主界面后自动开始后台增量检查。
- 启动期间没有确认弹窗，搜索页可进入。
- 未变化的成功文件不重新解析。
- 新增文件会被发现并最终可搜索。
- 修改文件会替换旧内容，搜索结果不出现新旧重复。
- 删除文件不再出现在搜索结果中。
- 禁用目录不会被自动更新。

### 11.2 首次索引并发搜索

- 首次索引尚未结束时，已成功提交的文件可以搜索。
- 搜索不会因为 `active_runs > 0` 自动禁用。
- 搜索结果明确标识为部分索引或当前已完成范围。
- 新解析结果发布后无需重启程序即可被搜索。
- 发布失败时旧索引仍可搜索，不能出现空索引。

### 11.3 冲突与恢复

- 首次索引运行期间新增或修改文件，只产生一个补偿增量任务，不产生并发重复索引。
- 文件在解析中被修改时，旧结果不会覆盖新内容。
- 文件在复制中或无权限时，索引继续处理其他文件。
- 删除搜索范围不会与正在写入的索引发生数据库竞态。
- 暂停、取消和程序关闭后可以从安全检查点继续。

### 11.4 性能与体验

- 自动更新不阻塞主窗口消息循环。
- 搜索操作不等待整个增量更新完成。
- 大量文件变化时事件会合并，不能每个事件创建一个任务。
- 进度始终显示完成数和当前已知总数，不能停留在模糊的“正在估算”。
- 单个异常文件不能触发全局错误弹窗或中断索引。

## 12. 开发交付物

1. 自动更新调度器及状态机。
2. 启动自动增量更新入口。
3. 文件监控事件与索引任务的合并、补偿和去重机制。
4. 搜索与后台写入的并发一致性处理。
5. 文件稳定性检查和源指纹提交校验。
6. 无感状态提示、进度和部分索引状态展示。
7. 任务恢复、异常记录和日志诊断。
8. 单元测试、并发集成测试和真实目录验收报告。

在“启动自动更新、后台搜索、首次索引冲突、异常不中断、任务不重复”全部验收通过前，不得标记为完全完成，也不得进入最终发行打包。
